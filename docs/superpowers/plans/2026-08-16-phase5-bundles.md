> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development or superpowers:executing-plans. Checkbox steps. Grounding: the 2026-08-16 recon — all mechanics verified there.

**Corrected facts this plan builds on:** new locations are born FULLY ENABLED (`features` defaults `{}` = everything on; the "SourceIt default-off" memory was manual practice, not code) — the bundle layer is what finally makes provisioning sane. The bundle hook is `shared/permissions.js` `isFeatureEnabledAtLocation` (:1116-1122) / tier-1 at `resolvePermission` :1172. The `bca_submit` precedent shows non-permission keys live happily in `locations.features` with `=== true` semantics. `plan_versions.features` validation + PlansAdmin UI pick up new `FEATURE_KEYS` automatically. `getLocationPlan` is NOT in any permission path (returns null for unpinned UN1T locations) — the per-location mirror is the thing to build; the resolver reads `locations.features` only.

**Design decisions (documented for PR review):**
- **Key→bundles is a SET with OR semantics**: a key is bundle-denied only when EVERY bundle owning it is explicitly off. Forced by reality: `email`/`whatsapp` belong to both `bundle_messaging` and `bundle_marketing`; `studio_management` to members+operations. Phase 4B's chrome split did NOT split the keys — don't invent new keys for this.
- **Bundle keys are `bundle_*` strings in `locations.features`** (deny-by-explicit-false, matching the existing polarity) — NOT WEB_PERMISSIONS entries. `module_cars` replaces nothing: `car_processing` maps to it 1:1.
- **Exemptions inherit**: notify keys stay exempt (correct); the 8 `approvals_*` sub-keys stay tier-1-exempt BUT the derived `approvals_inbox` and the Home queue respect bundles indirectly via their underlying surfaces — decision: approval CATEGORIES follow their owning bundle via a category→bundle map applied in the registry's visibility filter (an approver at a bundle-off location stops seeing those rows). Document + test.
- **Unassigned keys** (the 17: attendance_reports, assistant, contracts, glofox_import, preferences_import, bookkeeper, contact_linking, consultations, integrations_zoom_manage + approvals_*) get explicit homes: contracts→bundle_team; attendance_reports→bundle_team; glofox_import/preferences_import/contact_linking/consultations→bundle_sales? — NO GUESSING at execution: the implementer proposes the full 56-key table in Task 1's PR-visible constant with a comment per non-obvious assignment, reviewer verifies each against the page it gates. `settings`, dashboards, `issues_inbox`, `approvals_inbox` = never-bundled (core).
- **Team hub**: `bundle_team` exists but the Team ENTRY stays openToAll (policies is login-only); bundle-off hides the schedule/contracts TABS, not the hub. Comment it.
