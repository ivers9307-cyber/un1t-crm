# App usage (USAGE.1) — design

Status: draft for Richard's approval, 26 Oct 2026.

## Why

Richard wants to know how staff actually use the CRM: who signs in and when,
which features they use, for how long, and how many times a day. Nothing in
the CRM answers that today:

- `auth.users.last_sign_in_at` keeps one timestamp, and phone sessions stay
  signed in and refresh silently (7 staff show a sign-in in 30 days; 14 had
  a session refresh in 7).
- `audit_events` records data changes and some business actions, never a
  read or a screen.
- `device_tokens.last_seen_at` only moves on push registration.
- Vercel Analytics on the web is anonymous page counts.
- Nothing in `mobile/` or `src/` records screens.

## Goals

- Record each staff member's sessions (start, end, platform) and, within a
  session, each visit to a feature (feature key, start, end).
- Show, for a chosen range and studio: who used it, when they were last
  active, days used, sessions a day, total time, phone/web split; per
  feature: visits a day, average visit, total time; a one-day timeline with
  the trail.

## Non-goals

- Members, champ-app, the TV/kiosk surfaces, the studio PIN login.
- Action counts (sent a WhatsApp, approved a shift).
- Any record of which contact, booking or other record a screen showed.
- Real-time "who is online now".
- Alerts or scoring of staff from the data.

## Anti-goals

- Storing URLs, query strings, record ids, IP addresses or user agents.
- Recording a master while they impersonate or run a support session (the
  time would be filed against the person being viewed).
- Tracking that slows the app, or a tracking failure that the user sees.

## Data (one migration, service-role only)

All three tables: RLS on, no policy, `REVOKE ALL … FROM anon, authenticated`
(mig 677 default, stated explicitly). Nothing on the phone or browser reads
or writes them directly; every read and write goes through a route.

`app_usage_sessions`
- `id uuid` primary key, **generated by the client** so a re-sent batch
  upserts, never duplicates.
- `profile_id uuid` → `profiles(id)`.
- `location_id uuid` → `locations(id)`, nullable: the user's active studio
  when the session started (studio filter + day bucketing zone).
- `platform text` CHECK in (`phone`, `web`).
- `app_version text` nullable (phone only).
- `started_at`, `ended_at timestamptz`; `created_at`, `updated_at`.

`app_usage_visits`
- `id uuid` primary key, client-generated.
- `session_id uuid` → `app_usage_sessions(id) ON DELETE CASCADE`.
- `profile_id uuid`, `feature text`, `started_at`, `ended_at`.

`app_usage_daily`
- `id bigint` identity primary key; unique (`profile_id`, `day date`,
  `platform`, `feature`, `location_key uuid`) where `location_key` is the
  session's `location_id` or the nil uuid when it has none (so a person
  who works at two studios on one day gets a row per studio);
  `location_id` (nullable, the real FK), `visits int`, `seconds int`,
  `updated_at`.
- A row with `feature = '_session'` carries the session count and the
  union of session time for that day, so session totals do not have to be
  re-derived from visits. `platform` in daily is `phone`, `web` or `all`;
  only `_session` rows use `all` (the union across both platforms, which
  is the headline total).

Indexes: sessions `(profile_id, started_at)`, `(started_at)`; visits
`(session_id)`, `(started_at)`; daily `(day)`.

## Recording

**Feature keys.** One registry, `shared/usage-features.js`: every key with
its label, and two pure resolvers, `featureForWebPath(pathname)` and
`featureForPhonePath(pathname)`, mapping a route path to a key by prefix
(`/contacts/…` → `contacts`, `/settings/…` → `settings`, phone tab routes →
the same keys). An unmapped path resolves to `other`. Only the key ever
leaves the device. A test walks `src/app` and `mobile/app/(staff)` and fails
if a route resolves to `other` without being listed as deliberately
uncategorised, so a new screen forces a decision.

**Client tracker (shared logic).** A pure state machine in
`shared/usage-tracker.js` (testable without React): `start(platform)`,
`screen(feature, now)`, `pause(now)` / `resume(now)`, `drain()` → a batch
`{ session, visits[] }`. A screen change closes the current visit and opens
the next; consecutive same-feature screens merge into one visit. Visits
shorter than 2 s are dropped (navigation bounces). A batch includes the open
visit as "ended now", and the next batch re-sends it with a later end: the
server upserts by id, so the final value wins.

**Phone** (`mobile/`): a `UsageTracker` component mounted in the staff
layout (`mobile/app/(staff)/_layout.jsx`), so member screens never mount it.
`usePathname()` feeds `screen()`; `AppState` `active` starts a new session,
`background`/`inactive` ends it and flushes. Flush every 60 s while active,
via `api()` (keeps `authHeaders()`). Up to 60 s can be lost if the OS kills
the app; accepted.

**Web** (`src/`): a `UsageTracker` client component in `AppShell`, mounted
only for a signed-in staff user and not on public paths. `usePathname()`
feeds `screen()`; `visibilitychange` hidden or 5 min without input ends the
session, timed at the last input (the idle 5 minutes are not counted); input or visible again starts a new one. Flush every 60 s and on
`pagehide` / hidden with `fetch(…, { keepalive: true })`.

**Route** `POST /api/usage/events` (session cookie or Bearer JWT):
- `getCurrentUser()`; 401 if none. A user with no staff profile, a
  tombstone, a master, `impersonatingFrom` or `supportSession` set → `204`,
  nothing written (the client treats it as success and keeps no backlog).
- `validateBody` (Zod): one session + at most 200 visits; uuids, ISO times,
  feature in the registry, platform in the enum.
- Clamp: times no later than server now + 2 min and no earlier than 48 h ago
  (older batches dropped); a visit inside its session; any visit capped at
  4 h. Clamped rows are kept, not refused.
- A session id that already belongs to another profile → that batch is
  dropped (no cross-user overwrite).
- Upsert the session, then the visits, both checking `error`
  (`no-unchecked-supabase-write` armed on the new files).
- Recording is best effort: a failed write logs (`logError`) and answers
  503; the client keeps the batch and retries on the next flush (bounded:
  it keeps at most the last 10 batches).

## Roll-up and retention

Cron `app-usage-rollup`, every 15 minutes (`vercel.json`), with a
`cron_heartbeats` row in the same migration and `stampHeartbeat` on success:
1. Re-derive `app_usage_daily` for the days touched since the last run
   (today and yesterday in each studio's zone, via `@/lib/location-time`)
   from the raw tables, paginated (`.range()` + `.order()`). Re-deriving a
   whole day is idempotent, so a re-run or a late batch is always safe.
   A visit or session spanning midnight is split across the two days.
2. Once a day (first run after 03:00 platform time): delete sessions (and,
   by cascade, visits) whose `started_at` is over 90 days old, and daily
   rows over 400 days old. Paginated deletes.

Total time is the union of a person's time spans per day and platform,
not the plain sum: two browser windows, or phone and web at once, never
count the same minute twice within a platform. The "phone / web" split
shows each platform's union; the headline total is the union across both.
Feature time is the plain sum of that feature's visits (overlap there is
rare and visible in the timeline).

Days are bucketed in the zone of the session's studio (`zoneOfLocation`),
falling back to `PLATFORM_TZ` when a session has no studio.

## Reading

`GET /api/admin/app-usage?from&to&platform&location_id&view=people|features`
and `GET /api/admin/app-usage/[profileId]?from&to&platform&day=YYYY-MM-DD`,
both **master only** (`user.role === 'master'` on the real user; refused while
impersonating), cross-tenant like the rest of the platform console, narrowed by an
optional `organization_id` (and `location_id`, which must belong to that
organisation), 404 for an unknown person or a person outside the chosen
organisation.

- People view: from `app_usage_daily` for the range, joined in JS to the
  active, non-tombstoned, non-master staff of the chosen organisation (or
  of every organisation, each row labelled with its tenant)
  (`excludeTombstones`), so a person with no usage still shows (greyed).
  With a studio chosen: the people listed are those assigned to that
  studio (`profile_locations`) plus anyone with usage there, and the
  figures count only sessions that started there. "Last active" is the latest `ended_at` from
  `app_usage_sessions`.
- Features view: the same rows grouped by feature: people using it, visits a
  day, average visit, total time.
- Person view: per-feature rows from the daily table; the timeline for `day`
  from raw sessions + visits (only within 90 days; older days show
  "detail kept 90 days").
- Ranges: today, 7, 30, 90 days, 12 months.

Page: `/admin/app-usage`, in the Repset platform console: added to
`PLATFORM_TIER_PATHS` and the console nav in `src/lib/platform-nav.js`
(under Console, after Studio devices; `platform-nav.test.js` updated), so it
renders inside `PlatformShell`. Server component that redirects anyone but a
master; client component renders the approved mockup with existing
`@/components/ui` primitives, plus a tenant filter beside the studio filter
and a Tenant column in the "Who" table when all tenants are shown.
Registered in `src/lib/openapi.js`.

No new `WEB_PERMISSIONS` key (gated on master directly), so no mobile parity
entry is needed. No phone screen for the report (Richard reads it on the web).

### Draft handbook paragraph

> **App usage records.** The UN1T staff app and the CRM website record when
> you use them and which part of the app you have open (for example
> Contacts, Rota or WhatsApp), with the start and end time of each visit.
> They do not record what you type, which member or record you look at,
> your location, or anything outside the app. We use this to understand
> which tools are used, where training or improvements are needed, and how
> the app supports your work. Only the business owner can see it. Detailed
> records are deleted after 90 days and daily totals after 12 months. You
> can ask for a copy of your own records at any time.

## Builder's calls (flag for Richard)

- 2 s minimum visit; 4 h maximum visit; 60 s flush; up to 60 s loss on a
  killed app.
- "Times a day" = visits a day to a feature; consecutive screens within the
  same feature are one visit.
- Daily rows keyed per studio; studio filter = staff assigned there plus
  anyone with usage there.
- Total time = union of time spans (no double counting); idle web time
  ends at the last input.
- "12 months" range added to the filter because daily totals are kept that
  long.
