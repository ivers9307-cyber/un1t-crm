# un1t-crm — lessons learned & war stories

> Historical incidents and their fixes, moved out of `CLAUDE.md` (2026-06-25). Context for *why* certain patterns exist; the durable rules themselves live in the CLAUDE.md "Invariants" section.

## Lessons learned

**A database GRANT is a fence around the BROWSER's client. It says nothing about what a server page hands the browser.** `profiles` carries five comp columns and SECURITY.1 revoked them from `authenticated`/`anon` precisely so a staff member with devtools could not read them. `/settings/staff` then read `profiles` with `select('*')` through `createServerClient()` — `service_role`, which bypasses GRANTs the same way it bypasses RLS — and passed the rows into a client component as a prop. The columns crossed to every browser holding `settings` (manager, owner and master) inside the RSC payload. The fence was intact the whole time; the data went around it. Two things made it survive. **The page did not look like an HR surface** — it is a roster with names and locations, and nobody re-reads a `select('*')` on a page whose visible output is innocent. And **`check:location-scoping` is file-scoped**: its evidence check is satisfied by any properly scoped query in the file, so one scoped read greens the whole page. It was green on this page, and on `/settings/locations/[id]` and `/settings/staff/[id]`, throughout. It was found by reading the page during an unrelated row-scoping task, not by any gate.

The sweep that finds the rest is not "grep for `service_role`" — it is: **for every table that has ever had a GRANT revoked, find the reads that cross into a client component, and check whether they name their columns.** A `select('*')` that stays server-side and renders a few fields is fine; the same call handed to a `'use client'` component ships everything.

**Corollary, and the sharper half:** a column-level `REVOKE` is **silently ignored while a table-level GRANT exists** for the same role — no error, no warning. Supabase grants `SELECT ON <table> TO authenticated` table-wide by default, so mig 153's per-column `REVOKE` was a **no-op**, and mig 153b had to revoke table-level SELECT outright (which also future-proofs every column added later). Mig 153b's own `DO` block re-reads `information_schema.table_privileges` and raises if the grants are still there — that self-check is the pattern. **Verify a lockdown against `information_schema`, never against the migration text**: a `REVOKE` statement in a merged, applied migration is not evidence the privilege is gone.

**A `findBy*`/`waitFor` resolves on the DOM COMMIT, not after the passive-effect flush — so a `fireEvent` straight after an `await` can hit a WINDOW listener's previous closure.** MailSurface's j/k/e handler is a `window.addEventListener('keydown', …)` re-attached in a `useEffect` keyed on `conversations`/`selectedId`/`composeOpen`. RTL's async queries watch the DOM via MutationObserver, and the DOM shows the new rows at commit time — before React's scheduler runs the passive effects that re-attach the listener with the matching closure. Usually the wrapping `act` flushes effects before the test's next line; under CI scheduling it occasionally does not, and the very next keydown then ran against the MOUNT closure: an empty list made `j` a silent no-op (`neighbourId([]) → null`), the thread never opened, and the findBy timed out at exactly its 1000ms default between neighbour tests that ran in ~150ms (run 33270835641, 2026-08-29 — the tell that it was a logic race, not a starved worker). The same window is nastier in the modal tests: a stale `composeOpen=false` with a fresh selection would let `e` archive behind an open compose window — the exact bug the test pins — as a flake; and stale-`selectedId` closures made the typing-guard's "nothing happened" assertions pass VACUOUSLY (no-op for the wrong reason). **The fix is not a longer timeout and not a retry: flush pending effects (`await act(async () => {})`) before any `fireEvent` that relies on state an earlier await established** — `flushEffects()` in `MailSurface.test.jsx`. Click-driven tests are immune (row `onClick` gets fresh props); it is specifically window/document-level listeners attached in effects that carry this race. The component is fine as designed — a human cannot type inside a sub-millisecond effect-flush window.

**Removing a silent failure must never create a louder one. For a customer-facing message, LOSING the message is worse than the rare wrong value the guard was added to prevent.** BAREWRITE needed four review rounds to learn this, and every round found the same shape: a site was changed to "fail closed", and failing closed converted a rare silent-wrong-value into a CERTAIN loss of something the customer needed. Four instances shipped on the same branch, and all four were reversed before merge. (1) The WhatsApp STOP path stopped falsely acknowledging a failed opt-out — by returning early on the first failed write, so a partial failure wrote ZERO suppression signals where `main` had written one. A STOP that half-failed suppressed nothing. (2) `resolveEventCommsLocation` was made to throw on an unreadable `locations` row so a discarded read error could not route a message from the wrong brand's sender. `sendRaceConfirmations` is only invoked on a FRESH payment transition (`markRacePaymentStatus` returns `applied: null` once the payment is already `completed`), so nothing retried: a transient DB blip silently deleted a **paying** attendee's receipt and their check-in QR, inside an HTTP 200 no provider retries. (3) A send-once stamp, and separately the WhatsApp drip's recipient claim, were moved BEFORE the send to make them mutexes — converting a possible duplicate into a permanent silent loss on a process kill. (4) A lost bookkeeping write that `main` silently re-looped was surfaced as `result.error`, which reaches `campaignFailurePatch` and can mark a campaign `failed` — and `failed` is terminal, because the cron only picks `queued`/`sending`. **The order of preference:** log loudly and structurally (`logError`, never free text) → accept a duplicate or a retry → fail closed only where proceeding would do something actively harmful and irreversible. The lint rule is the ratchet that stops NEW instances; it does not need every existing site converted to fail-closed to be worth having, and visibility is the win.

**Before making a read throw, write down what the caller would have done with the `null` — and check whether the two answers can actually differ.** For `resolveEventCommsLocation` all three callers fall back to `event.location_id`, and the thing being chosen is a *sender identity*. Email identity resolves per ORGANISATION (`resolveEmailSender` → the location's `organization_id` → `tenant_email_domains`), and a host anchor is minted with its host's `organization_id` while the org master is by definition inside the same org — so the two are structurally the same email identity. SMS identity is *not* structural — the alpha sender is a per-LOCATION string, and inside UN1T Group **Hatch Street is `UN1THATCH` while Stillorgan is `UN1T Dub`**, so "same org ⇒ same sender" is simply false. What is true is narrower, and it is a claim about the DATA rather than the code: measured read-only against prod on 2026-08-20 over all 13 `race_events`, **no event resolves to a (target, fallback) pair whose alpha senders differ** — the one Hatch event is a plain event, so its target *is* its fallback. Give a Hatch event a host or a `sending_location_id` and the guarantee is gone; the resolver logs `crossesLocation` for exactly that, and `event-comms-location.js` carries the SQL that reproduces the measurement. **Two lessons, not one.** Price a guard against the harm it can actually prevent on real data, not against the harm you can imagine — *and* when the answer depends on data rather than structure, write down the query and the condition that ends it, because "it cannot differ" is the kind of sentence nobody re-checks.

**Corollary — a 5xx is a claim about the request, not a wish for a retry.** The obvious next move was to answer non-2xx from the payment webhook so the provider retried. It would have been *safe* (nothing claimed, nothing sent) and **inert**: both handlers only fire confirmations on a fresh state transition, and a redelivered payment is already `completed`, so the confirmation path is never re-entered. The 5xx would have bought retries that cannot deliver the message, while telling Revolut/Stripe we failed to process a payment state we **had** committed — and providers disable endpoints that keep failing. Check that the retry can actually reach the failed work before asking for one.

**A lost bookkeeping write is never grounds to KILL the work it belongs to.** The campaign cron's `campaignFailurePatch` flips a campaign to `failed` once `last_error` is already set and it is past the grace window — and the bundle-disabled gate writes `last_error` on **every** tick by design. So surfacing a lost rotation bump as `result.error` marked the campaign dead on its very first transient blip, needing an operator to resurrect it: a louder failure than the silent one it replaced. Bumps now return `result.warning`, which the cron logs at error level and counts but never feeds to the kill switch. The empty-audience finalise had the same defect for a subtler reason: it runs inside populate, so `send_started_at` is null, and the cron never clears `campaigns.last_error` — so any campaign carrying an older error was one blip away from `failed`, which is terminal because the cron picks only `queued`/`sending`. It is a warning too, and the campaign keeps `main`'s self-healing loop. **When you add a new failure signal, trace it into every escalation that already reads failure signals — and ask what the silent version actually did, because "it looped" is often the correct behaviour rather than the bug.**

**A number nobody can reproduce is not evidence, it is folklore — and folklore in `CLAUDE.md` is load-bearing folklore.** BAREWRITE published a repo-wide site count for the bare-write class four times: 477/201, then 582/264 vs 528/253, and an independent reviewer following the PR's own prescribed method measured 560/248 and 506/237. The *delta* was consistent; the absolutes never were, because "the same method" silently meant a different glob, a different ignore list, a different tree each time. One of those figures reached `CLAUDE.md`, where nothing would ever have re-derived it. This estate already knows the failure mode: the public-path invariant said "BOTH allowlists" when there were **four**, and that wording is why the defect it described kept recurring. So: **publish only what a reader can reproduce, put the exact command next to it, and run that command yourself before you publish the output.** Where no such command exists, publish nothing — an absent number costs a reader one measurement; a wrong one costs them a wrong decision they never think to check.

**Mocking the module under discussion at the seam is how two correct halves add up to a broken whole.** The resolver's suite proved it threw; race-confirmations' suite mocked the resolver and proved the throw was caught; neither asked what the customer received, and the receipt-deleting regression passed both. `race-confirmations.commslocation.test.js` now exercises the seam with the resolver **unmocked**, and every behavioural test in this area was run against the previous code and observed to fail before being kept.

**"Claim-first" is only a mutex if the write can actually fail — and a mutex on a send is a permanent-loss risk.** The WhatsApp drip's recipient claim was moved ahead of the send and documented as mirroring the blast sender. The blast `INSERT`s, so `UNIQUE(broadcast_id, contact_id)` rejects a concurrent pass; the drip `upsert`ed, which **succeeds on conflict** — it deduped across ticks and did nothing within them, and Vercel cron does not skip an overlapping run. The upsert was not gratuitous either (a `capped` row must be overwritable for the `CAPPED_RETRY_HOURS` retry), so the fix was one CAS per path rather than a revert: `INSERT` for a fresh contact, `UPDATE … WHERE status = 'capped' RETURNING id` for the retry. **That fix then had its own second half, and it took another round to see it.** A claim taken before a send is a lock, and a lock with no expiry is a permanent loss the moment the holder dies: a Vercel timeout between the claim and `sendTemplateMessage` left the row at `'pending'` with nothing sent, and nothing re-opened `'pending'` — not `fetchDripDoneContactIds`, not `claimDripRecipient`. It was defended as "a stuck `'pending'` is visible". It was not: the only figure that counts it (`unaccounted`) is rendered solely when the broadcast *also* has capped rows, and then it reads "have not been attempted yet". So the claim is now a **lease**: `created_at` is the claim stamp, an abandoned claim re-opens after `STUCK_CLAIM_MINUTES`, and the residual risk is a duplicate an hour later in the narrow case where the send reached Meta but the promote write did not. The race send-once stamps went the OTHER way for the same reason: that row is a bare timestamp with nowhere to hang a lease, so the stamp goes back AFTER the send with its error read and a CAS to detect a concurrent duplicate. **When a write is load-bearing as a lock: name the row count or the constraint that makes it exclusive, name what happens if the process dies while holding it, and — before claiming the stuck state is "visible" — open the component and find the line that renders it.**

**Dropping a key out of a reconciler's desired state is a DELETE, not a filter — and the deletion guard will not catch it.** The Zoom Phone contact sync enqueued the same ~12 creates every night from 2026-08-06 and Zoom refused every one (`400 … must be E.164 format`, 280 runtime errors in 7 days): nothing validated the number before enqueue, and a permanent 400 was retried like a transient one, so the nightly diff re-derived the identical jobs forever. The obvious fix — validate, and skip the bad numbers — is the trap. `diffContacts()` reads "in Zoom, not in desired" as a delete, so numbers that Zoom *accepted* before anything checked them (trunk-zero forms like `+4407502871075`) would have been silently deleted from the live directory the first night the validator shipped. `applyDeletionGuard()` is no defence at that scale: at 6,324 owned entries its threshold is `max(20, 5%)` ≈ 317 and the population is ~2, so the deletes sail through under it. ZOOMSYNC.4 passes the bad keys to the diff **explicitly** as `protectedKeys` — withheld from creates, updates *and* deletes — and the withholding self-clears: the set is recomputed from the CRM every run, so the moment the operator fixes the number the old key stops being produced, stops being protected, and the stale entry is deleted through the normal guarded path. **Validate at the enqueue, park at the worker, and make both visible.** The two halves cover for each other, and that asymmetry decides how strict the validator should be: over-rejecting silently strips real members off staff handsets, under-rejecting costs one Zoom 400 that the worker now dead-letters (`webhook_dead_letter`, provider `zoom_contact_sync`, deliberately absent from the replay registry for the same reason `postmark_queue` is — a replay would re-ask a settled question). Measured against the 6,339 live numbers: hard-E.164 + assigned-country-code + no-trunk-zero + IE/GB/NANP length bounds rejects **12**, almost exactly the nightly failure floor, whereas `libphonenumber-js`'s `isValid()` on full metadata rejects **69** — and ~56 of those are numbers Zoom is holding right now. That measurement is why no phone library was added: the library's *possible-length* data was worth reading at design time (IE 7-10, GB 7-10, NANP 10, copied into `NATIONAL_LENGTHS`), its validity verdict was not worth shipping, and it is lenient about exactly the trunk-zero splices Zoom rejects. **Three corollaries, each of which was a real defect caught in review of the same PR.** *A validator rule that says "this is wrong in every country" is almost always wrong itself.* The trunk-zero check asserted exactly that in its own comment; Italy has kept the leading 0 as part of the landline number since 1998 (`+39 06…`, `+39 02…`), and so do San Marino and post-2021 Côte d'Ivoire. Zero live exposure (prod's 4 Italian contacts are all mobiles) — but that is the shape of a latent false-reject, and in a directory the false-reject is the expensive direction, so the exception list is documented as deliberately non-exhaustive and widening it is the safe move. *Check every button that can clear the suppression, not just the one you designed.* Parking read `status='pending'`, so the **Discard** button — the operator saying "I am not going to fix this number", the one case where suppression must be permanent — was the only action that put the number back in the nightly diff, restarting the identical loop and adding a dead-letter row per night. The un-park must be `resolve` alone; everything else keeps suppressing. *A permanent-failure classifier needs a budget, because it cannot tell a bad record from a bad account.* A 4xx per number is triage; a 4xx on every number is a lost OAuth scope, a lapsed plan or a quota wearing the same status code. Without a cap, one credential fault converts into thousands of permanent per-number suppressions with no bulk undo — so past a small budget the worker stops parking and returns 500 instead. Prefer a loud transient over a quiet permanent: suppression is state, and outages should not be allowed to write state.

**The emailed login code is 8 digits, not supabase's default 6 — and a `maxLength` short of the real length fails as "wrong code", not as "truncated".** `MAGIC-LINK.2` shipped the mobile login-code field with `maxLength={6}`, `placeholder="123456"` and copy promising a 6-digit code, because 6 is what supabase's docs show. This project's Auth → Email → **Email OTP Length** is **8**. RN's `maxLength` silently drops the 7th and 8th keystrokes, the verify button lit up at 6 characters as designed, and `verifyOtp` then rejected a code the staffer had typed correctly — so the screen's own error copy ("That code didn't work — check it and try again") sent them to re-read the email, the one place the evidence looked fine. Passwordless sign-in was dead on mobile from the day it shipped, with only break-glass password sign-in working; nothing logged, nothing alerted, because every layer behaved exactly as written. **champ-app hit this first** (champ-app#16, 2026-06-19, "project issues 8, input was capped at 6") — same supabase project, same Magic Link template — and MAGIC-LINK.2 landed a month later having mirrored champ-app's *pre-fix* shape. A fix in a companion repo is not a fix in this one: the two apps share the project, not the code. The length now lives in `mobile/lib/otp.js` (`EMAIL_OTP_LENGTH`) and drives `maxLength`, the placeholder, the submit gate and the on-screen copy, so a dashboard change is a one-line follow — and the submit gate is an **exact-length** check, since a button that enables on a partial code is what disguised a truncation as a rejection.

**`.ilike()` used as a case-insensitive `=` is a wildcard injection — `_` and `%` are LIKE metacharacters AND legal email characters.** The codebase's idiom for "find the contact with this email" was `.ilike('email', value)`. But ilike takes a *pattern*: `_` matches any single character, `%` matches any run, and `normalizeEmail`'s regex (`/^[^@\s]+@[^@\s]+\.[^@\s]+$/`) accepts both. So `a_b@example.com` also matched `axb@example.com`, and `%@example.com` matched every address at the domain (`%@%.%` matched essentially the whole table; bare `%@%` is rejected — the domain needs a dot). Found 2026-08-07 in the **inbound-email webhook**, where the From address is unauthenticated and therefore attacker-controlled: `pickContact` then chose deterministically, so a stranger's mail was filed against a real contact and the ticket carried that person's identity — silently, never an error. The same shape was live in six other lookups, three of them on **public** routes: `validateMemberByEmail` (a lookalike address answered `is_member: true` and returned the real member's `contact_id` + `first_name` — and `%@domain` turned the endpoint into the member-enumeration oracle its own header comment says it prevents), `findOrCreateRaceContact` ×3 (public leads/class-booking/register forms link a team_member to whatever contact the pattern resolved — the same IDOR `restrictToLocation` exists to prevent, reached by another door), the unauthenticated `auth/log-event` actor lookup (mis-attributes an auth event to the wrong staff profile in the audit log), the Revolut webhook, and `matchSupplier` — whose comment literally claimed *"no % wildcards → exact"*, which was never true of an OCR-extracted supplier name and was false for `_` regardless.

**The fix is escaping, not `.eq()`.** Contacts are stored mixed-case, so `.eq()` on the raw value would miss legitimate matches; `escapeLikePattern()` (`src/lib/like-escape.js`) is behaviour-preserving for every address without a metacharacter and changes only the pathological ones. Escape the backslash *first* and in the same pass, or you re-escape what you just introduced. Note `.maybeSingle()` is **not** a guard: it errors on >1 row (so a broad `%` degrades to "no match"), but a `_` that matches exactly one *other* row returns that wrong row happily — and `.limit(2)`-style ambiguity checks have the same blind spot, since one wrong row is still one row.

**Why the test suite never saw it: every hand-rolled supabase fake modelled `.ilike` as `lower(a) === lower(b)`.** That is what the call site *means*, not what Postgres *does* — so under the mocks the attack payload matched nothing and every test stayed green. A fake that is stricter than production hides exactly the bug it exists to catch. `src/lib/like-escape.test-helpers.js` now provides a real LIKE evaluator (`ilikeMatches`) and the fakes use it; the wildcard tests were confirmed to fail against the unfixed code before being kept. `guardrails/no-unescaped-ilike-pattern` now blocks the shape at PR time: a deliberate substring search spells its wildcards in the source (`` `%${term}%` ``), so anything else is either escaped or annotated. Two footnotes worth keeping. **A strict validator changes the reachable payload set, so audit per route, not per pattern:** the `tickets/compose` route validates its recipient with the Zod `email` schema, which rejects a `%` local part — so only the `_` variant ever reached its query, while the inbound webhook's permissive `normalizeEmail` regex admitted both. **And a JS re-check makes the outcome safe without making the query correct:** compose already filtered candidates by exact match in JS and all 22 of its tests still pass with the escaping removed — it was never mislinking, but it was still fetching lookalikes and depending on one line of JS staying right forever. Escape the query *and* keep the re-check; two independent defences beat one clever one.


**Before reaching for an npm `overrides` entry, check whether the parent's declared range already admits the patched version — and check whether the feature that pulled the dep in is actually dead before deleting it.** Three HIGH SSRF advisories landed against `ip-address` (GHSA-mwp4-54f8-5fhr, -4xrf-jv44-h6hh, -22jq-vg5j-6vgg) reached via `imapflow → socks → ip-address`, and the Dependency audit job went red on every branch from 2026-08-04 to 08-07. Two instincts were both wrong. **(1) "imapflow's only consumer is the bank-recon agent, which is dead — just delete it."** It is not dead: `receipt-coverage-weekly` and `process-receipt-hunts` are live in `vercel.json`, BOTH have `cron_heartbeats` rows (migs 367, 370) so a silent death would page, `/accounting` is a real surface, and the last work on it shipped 2026-07-19 (RCOV #945, QSTASH.10 #941). Nothing in `docs/BACKLOG.md` marked it dropped. **Crons + heartbeat rows + recent commits beat a remembered "we're probably killing that" every time** — check them before deleting a dependency. **(2) "imapflow pins the vulnerable version, so we need an `overrides`."** It doesn't: `socks@2.8.9` declares `ip-address: ^10.1.1`, which already admits the fixed 10.4.0 — the lockfile was merely resolved at 10.2.0. The entire fix was `npm update ip-address --package-lock-only`: one lockfile line, `package.json` untouched, no override to maintain forever, and bumping `imapflow` itself would have done nothing (1.6.6 still depends on `socks@2.8.9`). **Read the parent's declared range first**; an `overrides` entry is only warranted when the parent genuinely pins. Gotcha found on the way: after a lockfile-only change, **`npm install` did not re-sync `node_modules`** (disk stayed on 10.2.0 while the lockfile said 10.4.0, so a local functional check would have tested the OLD code and passed for the wrong reason) — `npm ci`, which is what CI runs, is the authoritative install. Also: `npm audit --audit-level=high` gates on the PACKAGE severity while the `via` array mixes severities (here one high + two moderate), which matters for anything that parses the JSON.

**A permanently-red non-required check is worse than no check.** The audit job above stayed red for three days and PRs merged straight past it, because `main` has **no branch protection at all** (`gh api repos/:owner/:repo/branches/main/protection` → 404) — so "make it required" is not a checkbox, it's enabling protection for the first time, which would also make `gh pr merge --auto` start waiting instead of landing immediately. A second trap: this workflow has a `paths:` filter, and on GitHub a **required check that never runs blocks the PR forever**, so making it required also needs a skip-shim job for non-dep PRs. The cheaper fix that keeps the signal: an explicit `.audit-allowlist.json` (advisory id + reason + **expiry**) so a known-accepted advisory reads as ACCEPTED while a new one still fails, plus a tracking issue opened on *scheduled* failure — the scheduled run is the one that catches a new advisory against frozen deps and the one nobody sees, because it runs on `main` with no PR to hang a red X on. Expiry dates are what stop an allowlist from becoming a slow way to turn the check off.

**`supabase.auth.signOut()` deletes the PKCE code verifier — never sign out on the path to `exchangeCodeForSession()`.** auth-js `_removeSession()` removes three storage keys, not one: `${storageKey}`, `${storageKey}-user` AND `${storageKey}-code-verifier`. `signOut()` calls it for every scope except `'others'`, and it runs even when there is no session to remove, so a defensive "clean slate" sign-out silently destroys the verifier that the next `exchangeCodeForSession(code)` needs. Because @supabase/ssr pins `flowType: 'pkce'`, `?code=` is the shape Supabase puts on recovery and invite links, so this made password reset **100% broken** on `/reset-password` and `/host/set-password` from the moment the sign-out hardening landed — and it was invisible in tests, which mocked the client and so never modelled the storage side effect. The visible symptom was worse than the bug: the exchange failed, the user re-clicked the emailed link, GoTrue found the recovery token already consumed and bounced back to `#error=access_denied&error_code=otp_expired`, and the page — which only looked for `code` / `token_hash` / `access_token` — reported "this link is missing its verification token". Two rules out of it: (1) **order matters — establish the session first and sign out only on the failure paths**; the security property (a reset must not land on a different account that is already signed in) is better served by the fact that a successful exchange OVERWRITES storage with the link's user, plus a `getUser()` id check before the form unlocks and again at the moment of the write; (2) **always parse `error` / `error_code` / `error_description` off the callback URL** — an expired or already-used link is the single most common failure and must not be reported as a malformed one. Diagnosis path worth reusing: `auth.flow_state` (`authentication_method`, `code_challenge_method`, `auth_code_issued_at`) versus `auth.sessions` tells you exactly whether the link was consumed and whether the exchange ever produced a session; `auth.audit_log_entries` is empty on this project, so don't wait on it. Fixed in RESET-PKCE.1 — the handshake now lives once in `src/lib/recovery-link.js`; the host page used to be a *verbatim copy* of the staff page and therefore carried an identical copy of the bug, which is exactly why it is shared now.

**PKCE binds an emailed link to the browser that requested it.** Magic links and reset links carry a `code` that can only be exchanged with the verifier stored in the requesting browser. Opening the email in an app's in-app browser (Gmail's WebView on Android has its own cookie jar) or on a different device silently fails — this is a deliberate anti-CSRF property, not a bug, but it needs a message that tells the user what to do rather than the raw SDK error. If cross-device links ever become a requirement, the device-independent shape is `token_hash` + `verifyOtp`, which means changing the Supabase email template — a security-posture decision, not a refactor.

**When a third-party OCR vendor is the accuracy bottleneck, push structured fields instead of pushing the file.** We spent months relying on Xero's email-to-bills + Hubdoc OCR for supplier invoices and it was consistently wrong on UK/IE invoices — supplier names mangled, totals off, account codes missed. The fix wasn't a better OCR tier — it was inverting the flow: do the OCR ourselves with Claude Vision (which the operator was already reviewing), let the bookkeeper pick the exact Xero account + supplier inline from a cached chart-of-accounts + contacts list (Dext's posture), and then push a fully-formed `Type=ACCPAY/Status=DRAFT` invoice via the `/Invoices` API. End state: what the bookkeeper sees in `/invoices` is what arrives in Xero, byte-for-byte. Three-PR series XERO-API.1 → .2 → .3 (mig 186 + 187, PRs #53, #54, #55). The general principle: if a vendor's OCR is the worst link in your pipeline, replace it with structured payloads + a cache of the vendor's reference data, not with a different OCR vendor.

**Stacked PRs on GitHub don't auto-propagate to main — open every PR with `base=main`.** When you open a PR with `base=<feature-branch>` (the stacked-PR pattern), the merge lands the child's content INTO that base branch, NOT into main. If the parent has already merged into main BEFORE the child does, the child's merge becomes a dead-end commit on a stranded feature branch — the work never reaches production. This bit twice in the INVOICES-QUEUE.1 series: PR #47 was `base=invoices-inbox`, PR #49 was `base=invoices-queue-pr1`. Both reported `merged=true` to the API but nothing flowed to `main`. Recovery required a fresh `invoices-queue-pr2 → main` PR (#50) and a manual conflict-resolve merge. **The "cleaner diff" upside of stacked PRs isn't worth the stranding risk.** Default: always `base=main`, even when the new PR depends on an in-flight one. GitHub auto-deduplicates the diff once the parent merges — the child's diff narrows to just its own changes without any action from you.

**Shipping = branch + commit + push + PR. Stopping at the push is not shipping.** Pushing a feature branch without also opening a PR leaves the work in limbo — Vercel doesn't preview branches without a PR, CI doesn't run the `pull_request` workflow until the PR is opened, and the operator has to manually click through GitHub's "create PR" UI. The Cowork sandbox doesn't ship with `gh` but the GitHub REST API + curl is functionally equivalent — see the canonical loop in "Shipping from the sandbox" above. Whenever a change ships, the response to the user should include the PR URL, not just "I pushed it." This bit on the INVOICES.1 ship — the user explicitly asked "why no pr?" because the assistant stopped at `git push`. Now codified.

**Read vendor docs for the version you've pinned.** When integrating a third-party API (Revolut, Twilio, Stripe, etc.), always parse the OpenAPI spec / SDK source for the EXACT version you're targeting before writing client code. Don't work from cached knowledge of an older version. Two specific cases that bit on the Revolut integration: `capture_mode` enum casing (changed from `AUTOMATIC` upper-snake to lowercase `automatic` between versions) and the SDK token field name (`public_id` deprecated, replaced by `token`). Both produced misleading error messages that cost a round-trip with the user to fix. The OpenAPI spec is authoritative — if the docs page is a JS-rendered SPA that doesn't fetch cleanly, get the YAML from the vendor's openapi GitHub repo instead.

**supabase-js builders are thenables, not Promises — they have `.then` but no `.catch`.** The objects returned by `db.from(...)`, `db.rpc(...)`, `db.storage(...)` in @supabase/supabase-js v2 are PostgrestFilterBuilder / similar — they implement a custom `.then` to fire the underlying HTTP request when awaited, but they do NOT have a `.catch` method. The pattern `await db.rpc('foo', {...}).catch(() => {})` throws TypeError `e.rpc(...).catch is not a function` at runtime — `.catch` is invoked on the builder before the await unwraps it, and the builder doesn't have that method. The outer try-block (if any) catches the TypeError; the rpc itself never executes. This is a silent failure: error gets logged, downstream code thinks the rpc completed. **Right pattern**: `try { await db.rpc(...) } catch {}`. **Same caveat applies to**: `.from(...).insert(...)`, `.from(...).update(...)`, `.storage(...)`, anything returning a Postgrest builder. **Safe variants**: `db.from(...).insert(x).then(() => {}, () => {})` works because `.then` IS a method on the builder and returns a real Promise that has `.catch`. So `await db.rpc(...).then(() => {}).catch(() => {})` is also fine. **History**: bit us silently for 4 days (May 13–17 2026) until the pre-onboarding audit caught 728 stuck Postmark Open/Click events. Affected only the open/click webhook handlers + sequence step rpcs — Delivery / Bounce / SpamComplaint code paths used different patterns and were unaffected. Fix in HOTFIX #172 (see [docs/CHANGELOG.md](docs/CHANGELOG.md)). The whole src/ tree was swept; zero instances of the pattern remain.

**iOS auto-back-button only works WITHIN one navigator.** When you push from `(tabs)/X` into a screen under `app/X/[id]`, the destination lives in a different navigator from the tab — expo-router treats them as separate stacks. iOS's automatic back chevron only renders when the *current* navigator has a previous screen; cross-navigator pushes look like a fresh stack to iOS, so the chevron is absent (swipe-back gesture still works, but discoverability is gone). The fix is an explicit `Stack.Screen options={{ headerLeft: () => <BackHeaderLeft .../> }}`. Use the shared `mobile/components/BackHeaderLeft.jsx` — it handles `router.canGoBack()` and a `fallbackHref` for the cold-start push-notification case where the stack is empty. This bit twice already: pipeline + whatsapp (Apr 30, d442a36) and tasks + bookings (NOTIF.2). Whenever you create a new single-screen sub-stack that's reached from a tab, add the BackHeaderLeft.

**Mobile screens that cache fetched data must refetch on focus AND when the effective identity changes.** A React-Native screen that loads scoped data into state goes stale two ways: (1) the underlying data changes while the user is on another tab, and (2) a master starts/stops "View as user" (mig 035), which swaps the *effective* user server-side without changing the active location. Most tab screens are immune to (2) for free because they read `profile`/`activeLocation` from `useAuth()` and key their fetch effect on those objects — the auth context's `refresh()` (called on every impersonation start/stop) replaces those object references, so the effect refires and the API call re-issues with the impersonation header (`x-impersonate-target`). **The trap is an isolated child component that receives only `locationId`** (or any non-identity prop): it's blind to the identity swap, so during impersonation it keeps showing the operator's pre-impersonation data under a "Viewing as X" banner — looks exactly like a permissions leak, but it's a stale client cache (the door list itself IS server-scoped to the effective user; the data was just never re-fetched). This bit the Studio door card (#364): `DoorsCard({ locationId })` fetched via `useEffect([locationId])` with no `useFocusEffect`, so when impersonation started without a location change it never refetched the `unifi_door_ids` allowlist. Its sibling `AcDeviceList` looked identical but was saved by its `useFocusEffect` — that's the "AC updated but doors didn't" asymmetry. **Convention for any mobile component that fetches scoped data:** (a) extract the fetch into a `load` useCallback; (b) `useFocusEffect(useCallback(() => load(), [load]))` for tab-return freshness (silent — no spinner, keep current data on screen until the new data lands); (c) if it's an isolated child, key it on the identity (`key={\`${profile.id}:${activeLocation.id}\`}`) so it remounts the instant impersonation toggles. `mobile/components/AcDeviceList.jsx` is the canonical pattern. #364 fixed the door card; #365 brought the rest of the persistent tabs (schedule / pipeline / bookings + the three Home dashboards) in line so the app is uniformly fresh-on-focus. (A full audit confirmed no other *stale-cache* surface was affected — detail screens mount fresh per navigation. ⚠️ That same audit also called `expenses`/`invoices` safe because they "derive identity server-side via `getCurrentUser()`" — true, but it missed a *different* bug class: their mobile API clients hand-rolled request headers and never sent `x-impersonate-target`, so `getCurrentUser()` resolved the real master, not the target. See the next lesson / #382.)

**Mobile `/api/*` client wrappers must build headers through the shared `authHeaders()` / `api()` helper — hand-rolling a `Bearer` header silently drops `x-impersonate-target` and breaks "View as user" (#382).** Mobile impersonation rides on the `x-impersonate-target` request header (the counterpart of the web impersonation cookie); `getCurrentUser()` only honours it when the request actually carries it, and only for a master session. `mobile/lib/api.js`'s `api()` attaches it automatically, but six wrappers (`invoices` / `expenses` / `contracts` / `checklists` / `issues` / `policies-api.js`) bypassed `api()` and built `{ Authorization: Bearer … }` inline — so every call they issued during a "View as user" session reached the server as the *real* signed-in user. Since only masters can impersonate, a master viewing-as a staff contractor opened Invoices and saw the whole location's review queue (another contractor's submitted invoice) instead of the empty list the target should see. It reads like a scoping leak, but it's the impersonation header never arriving — real staff on their own logins (no header, and the server ignores it for non-masters) are correctly scoped, and **web is immune** because its httpOnly impersonation cookie is sent automatically on every same-origin request. Fix: one impersonation-aware builder — pure `buildAuthHeaders()` in `mobile/lib/api-headers.js`, async `authHeaders()` in `mobile/lib/api.js` (session token + `readImpersonate()`), every wrapper routed through it, and `mobile/lib/impersonation-headers.test.js` asserts all six forward the header. **Rule: never hand-roll a Bearer header in a mobile `/api/*` wrapper — `import { authHeaders } from './api'`** (pass `{ json: true }` for a JSON body; pass nothing for multipart so RN sets its own FormData boundary; `{ locationId }` to override the active location). The web import-resolution and parity linters won't catch a missing header — only this convention does.

**Never embed `profiles` from a mobile-direct Supabase select — the `authenticated` role has NO SELECT grant on `public.profiles`, so the embed 500s with "permission denied for table profiles".** Web API routes use the service-role client (RLS-bypassing, table grants irrelevant), but the mobile app (`mobile/lib/*-api.js`) talks to Supabase with the anon-key + JWT **`authenticated`** client, which is bound by BOTH RLS *and* table-level GRANTs. `public.profiles` is granted to `postgres` / `service_role` only — deliberate, for salary/comp privacy — so a PostgREST embed like `assignee:profiles!activities_assignee_id_fkey(full_name)` makes the **whole** select fail. Note the asymmetry: a GRANT denial **hard-errors** the request, whereas an RLS denial on an embed just **null**s the joined resource — so this fails louder than the usual RLS-scoping behaviour and takes the entire screen's data with it. This 500'd the Tasks tab (#371): `tasks-api.js` `TASK_SELECT` embedded the assignee profile. Fix was to drop the embed — on a "my tasks / my X" mobile surface the embedded user is always the signed-in user anyway. **Rule:** if a mobile screen genuinely needs *another* user's name, route it through an `/api/*` endpoint (service-role) rather than embedding `profiles` client-side. `contacts` IS granted to `authenticated`, so `contact:contacts(...)` embeds are fine — this is specifically a `profiles` (and any other service-role-only table) constraint.

**A mobile file that imports a name its target module doesn't export resolves to `undefined`, and only crashes at runtime — nothing in the pre-merge pipeline catches it.** Web's equivalent is caught by `next build` (the import-resolution note under "Before pushing"), but the mobile chain has no such gate: vitest doesn't load RN screens, the root ESLint config **ignores `mobile/`**, and **`expo export` (Metro) silently tolerates undefined imports** — it bundles them clean. So a bad import passes every check and OTA-ships, then throws on a real device. This caused the 2026-06 Schedule crash: `schedule.jsx` did `import { MANAGER_ROLES } from '../../../shared/permissions'`, but that file never exported `MANAGER_ROLES` (it lives in the web-only `src/lib/schemas.js`). The value was `undefined` — latent for weeks because `isManagerRole()` was only reached via `canAdjust` (needs a rendered shift), until the Manage segment (#375) called it on **every** Schedule render → `undefined.includes(...)` → `Cannot read property 'includes' of undefined`, Schedule tab down for every user. **Guard added after:** `npm run check:mobile-imports` runs `eslint-plugin-import`'s `import/named` family over `mobile/` via the dedicated `eslint.mobile-imports.config.mjs` (node_modules ignored, so only local cross-module imports are validated — no react-native/expo false positives). **Post-SDK-57 update:** the seam is now the `shared` file: package, and that nearly killed this guard silently — the resolver returned the *symlinked* `mobile/node_modules/shared/*` path, which matched `import/ignore: node_modules` and exempted exactly the imports the guard exists for (probe-proven: a bogus `shared/permissions` name exited 0). The config now sets `preserveSymlinks: false` (realpath escapes node_modules) plus an absolute repo-root `paths` fallback (Web CI never installs `mobile/node_modules`, so without it 'shared/*' is unresolvable there and the guard no-ops). If you touch the resolver settings, re-run the probe: `import { NOPE_XYZ } from 'shared/permissions'` via `--stdin` MUST exit 1. It's a Web CI step, and **`mobile/**` now triggers Web CI** (it didn't before — the other half of why this reached prod). **When you hit a mobile import error the fix is usually local:** the mobile bundle can't import web-only modules (`src/lib/*`), and not everything is re-exported from `shared/` — verify the named binding actually exists in the target file (e.g. role constants like `MANAGER_ROLES` get defined inline in the mobile screen).

**Metro 0.84 (Expo SDK 57) does not resolve relative imports that escape the project root — watchFolders is not enough.** Pre-SDK-57, mobile imported the seam as `'../../shared/x'` and a `watchFolders: [../shared]` entry in metro.config.js made it resolve. Under SDK 56+'s on-demand file map, lazy file discovery is *scoped to the project root*, so those escapes died with "Unable to resolve" (and, half-fixed, "Failed to get the SHA-1"). Neither watching the sibling folder nor watching the monorepo root nor a custom `resolveRequest` fixes it cleanly — the supported route is making the out-of-root code a real package: `"shared": "file:../shared"` (npm installs a symlink; Metro's symlink resolution is always-on and not subject to the root scoping). Keep `watchFolders: [sharedRoot]` anyway — it's what makes shared/ edits hot-reload in dev. Disabling the file map (`experiments.onDemandFilesystem: false`) also works but is a deprecated-era escape hatch; the package is the right shape.

**Per-vendor specifics that bit hard:**

- **Twilio's Irish long codes are voice-only.** All Irish providers (not just Twilio) face this — the carriers don't accept A2P SMS over local Irish numbers. Alphanumeric sender IDs are the canonical solution for sending SMS to Ireland from a non-Irish entity. Don't waste time looking for Irish SMS-capable numbers in any provider's catalog.

- **Revolut sandbox vs prod is fully separate** — separate dashboards (`business-sandbox.revolut.com` vs `business.revolut.com`), separate API keys, separate webhook secrets. Mismatching env vars across the trio (`REVOLUT_API_KEY`, `REVOLUT_API_BASE_URL`, `NEXT_PUBLIC_REVOLUT_MODE`) causes the SDK iframe to silently render blank instead of throwing a clear error.

- **Twilio trial accounts can only send to verified numbers** (Phone Numbers → Manage → Verified Caller IDs). Adding a payment method flips to paid and lifts the restriction. Alphanumeric senders are blocked entirely on trial.

- **Vercel doesn't auto-redeploy on env-var changes.** Every time the user changes a Vercel env var, they need to manually redeploy. Document this in instructions.

- **Layout auth gates run before pages.** Anything under `src/app/<segment>/` inherits the layout's auth check. Public pages must live OUTSIDE any auth-gated segment — see the deposit page move from `/cars/deposit/[token]` to `/deposit/[token]` in mig of May 2026.

- **Postgres webhook retries should never reset state.** Webhook handlers must be idempotent. Always check "is this state already final?" before stamping timestamps. Always return 200 for unrecognised events so the upstream provider doesn't auto-disable the hook (Revolut, Stripe, Postmark all do this).

- **AppShell has its own publicPaths allowlist** (`src/components/AppShell.jsx`) separate from middleware. Adding a new public-facing page requires adding it to BOTH the middleware auth allowlist AND the AppShell sidebar-suppression list, otherwise the buyer either gets bounced to login OR sees the CRM sidebar.

- **Both consent flag families exist for a reason.** `email_marketing` / `whatsapp_marketing` (broadcasts) vs `email_administrative` / `whatsapp_administrative` (transactional). Reminder code paths check the `_administrative` flag; opting out of marketing should never block a booking reminder.

- **WhatsApp template categories are policy, not just labels.** Sending a MARKETING template under a transactional pretext (e.g. as a reminder) is a Meta policy violation that gets accounts in trouble. Reminder + utility flows refuse MARKETING templates at the picker AND at runtime as a backstop.

- **Two-sided secrets need monitoring.** When a secret has to match between two systems we control (Vercel `CRON_SECRET` + `private.app_config.cron_secret`), drift is silent and only surfaces when something downstream notices. The fix isn't "be careful when rotating" — it's "the system tells us within minutes when something stops working". Pattern: every cron writes a heartbeat on success, a view computes is_stale, a single health-check endpoint 503s when anything is stale, an external monitor pings the endpoint. See "Cron monitoring" under Deployment.

- **Supabase views default to SECURITY DEFINER.** Any view created in a migration runs with the postgres role's permissions and bypasses RLS on the underlying tables. The advisor (`get_advisors` MCP, type=security) catches it as an ERROR-level lint. Always include `WITH (security_invoker = on)` on `CREATE VIEW`, or follow up with `ALTER VIEW ... SET (security_invoker = on)`.

- **Cowork sandbox has filesystem and auth restrictions worth knowing about.** Specifically: it can't `unlink()` files by default (fix via `mcp__cowork__allow_cowork_file_delete` — don't tell the user it's impossible), it has no GitHub credentials so `git push` needs an explicit PAT + credential helper setup, and the GitHub MCP server doesn't support DCR so the auto-OAuth flow can't be initiated by Claude. Full operational guide and the working-pattern recipe are in the "Working from Cowork (Claude sandbox notes)" section above. None of this applies if using Claude Code in the user's terminal — it's Cowork-specific.

- **Next 14 caches third-party fetch responses inside the data cache, even on `force-dynamic` routes.** **No longer applies under Next 16** — Next 15+ defaults `fetch()` to `cache: 'no-store'`, so the workaround was retired in NEXT.16-CLEANUP (#179). Keeping the lesson here as durable institutional memory; the failure mode was subtle, the recovery path saved real customer-facing incidents. Original write-up: `dynamic = 'force-dynamic'` opts the route into dynamic rendering and sets fetch defaults to no-store FOR fetches issued by the route's own code. The Supabase JS client opens its own internal fetch instance that doesn't inherit those defaults. Symptom: an UPDATE in Postgres is invisible to the next read on the same deployment until the data cache evicts (or you redeploy). Hit this on 2026-05-05 when extending a deposit token's expiry — the DB row was correct, the API kept returning `TOKEN_EXPIRED` from a stale cached fetch, and `x-vercel-cache: MISS` is no help here because the cache lives at the data-cache layer, not the CDN. Original fix landed in `src/lib/supabase.js` — `createServerClient()` passed `{ global: { fetch: noStoreFetch } }` so every read was fresh. The `noStoreFetch` wrapper plus the `fetchCache = 'force-no-store'` and `revalidate = 0` page exports were all removed in NEXT.16-CLEANUP once the framework default flipped. If a similar caching-mystery shows up under Next 16 or later (someone reads stale data right after a write), the suspect class is the same: a third-party SDK doing its own internal fetches that don't honour a route-level `cache: 'no-store'`. Modern fix is either pass `{ cache: 'no-store' }` explicitly on the inner fetch, or wrap the route's call in `unstable_cache` with a tag and bust the tag on writes.

- **Every cron with a heartbeat row MUST stamp the heartbeat in its route.** A cron can be firing fine (Vercel logs show 200s every tick) and still go "stale" because the route forgot to call `stampHeartbeat()`. The health-check correctly raises 503 — the cron itself is dead in the heartbeat sense even though it's alive in the run sense. Hit this on 2026-05-05 with `race-timing-events`: the row was seeded by mig 097 with `last_ok_at = NOW()` and immediately started the slow drift to staleness because the route never refreshed it. Pattern check: `grep -L stampHeartbeat src/app/api/cron/*/route.js` should return only `health-check/route.js` (the checker itself, not a stamper) and `ad-insights-backfill/route.js` (manual-only backfill: no vercel.json entry and no `cron_heartbeats` row, so there is nothing to stamp — re-confirmed by the CRON-HB-AUDIT.1 audit, mig 406). Anything else on that list is a latent staleness bug — unless it has no heartbeat row *and* no schedule, in which case it's the opposite trap: seeding a row for an unscheduled manual route makes it read permanently stale.

- **Per-domain branding on a single Next app uses the location-id as the brand key.** un1t-crm runs on two hostnames — `crm.un1tdublin.com` (UN1T) and `pay.ccfautos.com` (CCF Autos). The deposit page on the pay.* hostname needs CCF branding; UN1T pages need UN1T branding. We don't switch on Host header — we switch on the car's `location_id` because the same hostname can technically serve any location's car. Pattern: `app/deposit/[token]/page.js` has a server-side `generateMetadata({ params })` that joins `cars → locations → company_settings` and returns `icons` + dynamic title; the page component renders `branding.logo_url` at the top of the layout. Same approach for any future buyer-facing page on a brand hostname — branch on the source row's `location_id`, not the request hostname.

- **PostgREST embedded-resource filters are brittle under count-only selects.** A query like `.from('contacts').select('*, contact_preferences!inner(*)').eq('contact_preferences.email_marketing', true)` works when you await full rows. The moment you overlay `.select('id', { count: 'exact', head: true })` to get just a count, the embedded `contact_preferences` filter silently loses its binding and counts return **0 with no error**. Keeping the same embed shape in the count select (`.select('id, contact_preferences!inner(id)', ...)` or even `.select('*, contact_preferences!inner(*)', ...)`) doesn't help — head:true changes the semantics in a way that drops the relationship link. Don't fight this. **Denormalise the columns you filter on** into the parent table and filter the parent as a single-table query. Mig 155 added `contacts.email_marketing` (denormalised from contact_preferences via trigger) and `contacts.pipeline_stage_slug` (denormalised from deals via trigger) specifically to kill this whole class of bug. CAMPAIGN.6→.9 each tried to fix the symptom inside the embed approach and each exposed a new seam (zero-row counts, URL-length 400s, etc.) before we conceded and denormalised. If a future audience query needs a field that isn't already on `contacts`, the answer is "denormalise it via trigger", not "make the embed work."

- **A bare PostgREST embed (`contacts(...)`) breaks the moment a table gains a SECOND foreign key to that resource — it returns HTTP 300 / `PGRST201` ("more than one relationship was found"), NOT rows and NOT a clean app error.** The RADAR-AGENT feature added `agent_verified_contact_id` to `whatsapp_conversations` + `instagram_conversations`, so each now has TWO FKs to `contacts` (alongside `contact_id`). Every route that embedded `contacts(...)` bare silently started erroring: the WhatsApp/Instagram **send** route surfaced it as a misleading `Conversation not found` 404 (its conversation lookup errored), and the **list/detail** routes returned empty — i.e. the operator saw "WhatsApp inbox: 1 unread conversation" but opening it showed an empty thread and replies failed with "couldn't send, conversation not found." Mobile was immune because `mobile/lib/whatsapp-api.js` already disambiguates (`contacts:contact_id`), which is the asymmetry that pins it (reads work, the shared web `/send` route doesn't). **Fix: always disambiguate a contacts embed by the FK column — `contacts!contact_id(...)`.** The `!hint` does NOT alias, so the result key stays `contacts` and every client's `.contacts` access is unchanged. Verified live against the project's PostgREST: `?select=id,contacts(id)` → `300 PGRST201`; `contacts!contact_id(id)` → `200`. Shipped in WHATSAPP-INBOX.1 (#417) across all 7 affected embeds (4 WhatsApp + 3 Instagram). **Tables with ≥2 FKs to `contacts` today: `whatsapp_conversations`, `instagram_conversations`, `team_members`** — a new bare `contacts(...)` embed on ANY of them will 300. Audit the whole class with `select conrelid::regclass, count(*) from pg_constraint where contype='f' and confrelid='public.contacts'::regclass group by 1 having count(*)>=2;`. General rule (not just contacts): **the instant a table has two FKs to the same target, every bare embed of that target must be disambiguated with `!fk_column`** — and watch for a 2nd FK being added to an existing table (an agent/verification/audit column), which silently breaks embeds that were fine the day before.

- **Booking `start_time` + `booking_date` are Dublin wall-clock, not UTC.** The `bookings` table stores `booking_date` as `YYYY-MM-DD` and `start_time` as `HH:MM:SS` — both are operator-local Dublin time without any timezone semantics in the DB. **Never** build a Date from them with a `Z` suffix (`new Date(\`${dateStr}T${timeStr}Z\`)`) — that forces UTC parsing, then formatting the resulting instant in Europe/Dublin adds the BST offset (+1h March→October), so a 17:00 booking renders as 18:00 in the confirmation SMS. Use the time string verbatim and only go through `Intl.DateTimeFormat` for the weekday/date label (anchor on noon UTC of the booking date — safe across timezones). Hit this in BOOKING.2 (commit `13452dc`); the fix lives in `src/lib/booking-confirmations.js` `fmtBookingTime()`. Same convention applies to anywhere else you find these two columns being composed into a Date.

- **`/api/public/book` must copy `event_type.location_id` onto the booking insert.** Operator hit this on 2026-05-13 — Sarah's consultation booking didn't appear in `/bookings` because the location-scoped query filtered out rows with `location_id IS NULL`, and the public booking insert was loading `event.location_id` for downstream consent + Glofox push but never writing it onto the booking row itself. Fix: explicit `location_id: event.location_id` in the insert payload (BOOKING.1, commit `13452dc`); mig 154 backfilled existing rows. **Rule of thumb:** any insert into a tenant-scoped table whose source data already carries a `location_id` must propagate it, even if a downstream consumer (Glofox push, sequence trigger) reads it via the parent's join. The /bookings page reads the booking's own `location_id`, not the event_type's.

- **Vercel runtime log viewer truncates `console.log` output.** The MCP `get_runtime_logs` tool only shows the first/last log line per request — anything you `console.log` mid-handler is captured but invisible in the table view. For diagnostic logging, **embed the data in the API response itself** under a `_debug` key and read it from DevTools → Network → Response. CAMPAIGN.7 burned a round-trip pushing console diagnostics that couldn't be read; CAMPAIGN.7b switched to response-body diagnostics and found the bug in one refresh.

- **postgrest-js's `.select()` has two overloads — only the FIRST one reads options.** `PostgrestQueryBuilder.select(columns, options)` (the first `.select()` after `.from()`) reads `options.head` + `options.count`, switches method to HEAD, adds `Prefer: count=exact`. `PostgrestTransformBuilder.select(columns)` (any `.select()` chained AFTER a filter like `.eq` / `.not` / `.in`) takes ONLY a columns argument — a second argument is silently ignored, JS doesn't enforce arity. The pattern `db.from('x').select('*').eq(...).select('id', {count:'exact', head:true})` looks like it should give you a HEAD count request, but the chained `.select` is the no-options TransformBuilder overload — it just resets `select=id` and you keep your method=GET with no count Prefer. Supabase-js parses `count` as `null` and `count || 0` renders 0. CAMPAIGN.10 traced this; the fix is to request `head`+`count` on the FIRST `.select()` only. **When supabase-js returns 0 from a count query but you expect rows, check whether you're chaining `.select()` twice.**

- **Supabase / PostgREST has a default 1,000-row select cap.** Every `await db.from('x').select(...)` returns at most 1,000 rows unless you explicitly `.range()` past it. For any fan-out (campaign send, contact import, bulk webhook handling, sequence enrollment), page with `.range(from, from + N - 1)` until a short page comes back. CAMPAIGN.11 was a 1k-vs-3k silent send because the audience query happily returned 1,000 rows and downstream code never asked for more. CAMPAIGN.11-RECOVERY's first attempt hit the same cap on a *different* query (the `campaign_recipients` lookup to find already-sent contacts) — assume every unbounded select is capped until proven otherwise.

- **`PostgrestFilterBuilder` instances are single-use.** Awaiting once consumes the thenable. To page or to re-run the same query against different `.range()`s, **rebuild the builder per iteration** — don't try to reuse a single builder reference. Tag-filter resolution / audience-filter application is cheap; this re-build cost is negligible.

- **`.update().eq()` in supabase-js MUST be awaited or it never fires.** The filter builder only dispatches an HTTP request when its thenable is consumed (await / `.then`). An "update" tucked inside an outer `.then()` without `await` looks correct but is a silent no-op. CAMPAIGN.12 hit this in 4 places — every campaign rollup counter (opens/clicks/bounces/complaints) stuck at 0 for months because of `await db.from('campaigns').select(...).single().then(({data}) => { db.from('campaigns').update(...).eq(...) })`. Fix is either `await` the inner builder or — better — replace the read-then-write with an atomic RPC like `increment_campaign_metric`.

- **High-volume webhook handlers must defer work.** Postmark fires Delivery + Open + Click + Bounce events per recipient. A 3k-recipient campaign produces ~5k webhook calls in 20s. If each handler does 3-5 sequential DB writes inline, Vercel's lambda concurrency limit trips and webhooks 5xx before reaching your code — Vercel's "Massive burst, 8x faster failures, no error logs, platform/validation level" alert is the tell. **Pattern that works:** webhook handler does auth + dedup + 1 INSERT into a queue table + return 200 (under 50ms). CAMPAIGN.13's `postmark_webhook_queue` + `process-postmark-webhooks` cron is the reference shape.

Lowercase-normalise emails for comparison; `contacts.email` is stored lowercase already so a direct `.in()` matches. UNSUB.4 is the reference pattern — reconciled 23 contacts in one run.

- **Don't mix local-time Date parsing with UTC ISO formatting.** `new Date('2026-05-04T00:00:00')` (no `Z` suffix) is parsed as LOCAL time; `new Date('2026-05-04T00:00:00Z')` is UTC. - **Wrap `auth.uid()` (and `auth.role()` / `auth.jwt()`) inside `(SELECT …)` in every RLS policy.** A raw `auth.uid()` call in a policy's USING / WITH CHECK clause is re-evaluated **per row** during a query — PG treats it as a stable function but doesn't fold the call into an InitPlan when it's not subqueried. ## Working from Cowork (Claude sandbox notes)

When Claude is operating on this repo from inside Cowork mode, it runs in an isolated Linux sandbox that bind-mounts the host's `/Users/richardivers/code/` at `/sessions/<sandbox-id>/mnt/code/`. **The sandbox can read and write files but cannot `unlink()` by default.** First-time symptom: `rm` fails with `Operation not permitted` (EPERM, not EACCES — important, because EPERM means "the operation isn't allowed for this user" rather than "permissions deny it"). Files the sandbox just created with `touch` and 0600 perms still can't be removed. This is a deliberate Cowork safety guardrail at the bind-mount layer — `chmod`, `chown`, `chflags`, ACL edits do nothing because the restriction is above the host filesystem. **The fix is `mcp__cowork__allow_cowork_file_delete`** — call it with the path Claude was trying to delete, the user gets an approval prompt scoped to a directory (`code` in our case), and from that point forward `unlink()` works for everything under the approved dir. This unblocks not just `rm` but also `git gc`, `git reset --hard`, `git checkout` of a branch with deleted files, etc. — anything that needs to delete files. **Default response when an `rm` fails should be to call this tool, not to tell the user it's impossible.**

**`git push` from the sandbox needs explicit credential setup** — the sandbox `HOME` is `/sessions/<sandbox-id>/`, has no `~/.gitconfig`, no `~/.ssh`, no `gh` CLI, and no credential helper. Default `git push` over HTTPS fails with `could not read Username for 'https://github.com'`. The pattern that works (committed-on-disk PAT + sandbox-only credential helper):

1. Fine-grained PAT lives at `/Users/richardivers/code/.github-pat` (one level above the repo, so it's outside `un1t-crm/` and can't accidentally be committed). 0600 perms. **Never moves into the repo, never enters chat history, never goes into a remote URL.** From inside the sandbox the same file is at `/sessions/<sandbox-id>/mnt/code/.github-pat`.
2. PAT permissions for the un1t-crm repo specifically (do NOT grant "All repositories" scope):

   | Permission | Level | Why |
   |---|---|---|
   | Metadata | Read | Required, auto-added |
   | Contents | Read and write | Push commits, create branches, fetch history |
   | Pull requests | Read and write | Open / comment / merge PRs |
   | Actions | Read | See CI status before suggesting merges (optional but cheap) |

   Skip Issues, Workflows (the `.yml` files), Secrets, Variables, Webhooks, Pages, Discussions, Deployments, Codespaces, Packages. Account-level permissions all "No access". Token expiration: 90 days, set a calendar reminder to rotate.

3. Credential helper script in sandbox `/tmp` (sandbox-only path so it never affects the user's terminal git):

   ```bash
   cat > /tmp/git-cred-helper.sh <<'EOF'
   #!/bin/sh
   case "$1" in
     get)
       echo "username=x-access-token"
       printf "password=%s\n" "$(tr -d '\n' < /sessions/<sandbox-id>/mnt/code/.github-pat)"
       ;;
   esac
   EOF
   chmod +x /tmp/git-cred-helper.sh
   ```

4. Push with the helper inline (avoids persisting any credential config to `.git/config`, which would break the user's terminal git):

   ```bash
   git -c credential.helper="/tmp/git-cred-helper.sh" push origin main 2>&1 | sed 's|github_pat_[A-Za-z0-9_]*|github_pat_REDACTED|g'
   ```

   The `sed` filter is belt-and-braces in case git ever logs the URL with creds in an error path. Real PAT tokens start with `github_pat_` (fine-grained) or `ghp_` (classic) — both should be redacted before output is shown to the user.

The sandbox ID also changes between sessions, so `/sessions/<sandbox-id>/...` paths can't be hard-coded — derive from `pwd` or `$HOME` at runtime.

**If you're using Claude Code (CLI) instead of Cowork, none of this applies.** Claude Code runs natively in the user's terminal with their actual `~/.gitconfig`, `~/.ssh`, and `gh` CLI — `git push` just works. The sandbox-specific knobs (PAT helper, file-delete permission tool) are Cowork-only operational concerns.
