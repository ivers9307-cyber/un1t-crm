# Scheduled jobs and webhooks

The full rules behind the one-line summaries in `CLAUDE.md`. Moved here word for word from `CLAUDE.md` on 19 Nov 2026 (CLAUDEMD.1); keep the two in step when a rule changes.

**Crons & webhooks**
- **A new cron is `export const GET = defineCron({ heartbeat: '<row>' }, run)` (`src/lib/define-cron.js`, CRONWRAP.1) plus its own `export const maxDuration`**: the wrapper owns the secret check, the error boundary and the stamp, and `run` returns `{ ok: false }` only when the RUN failed, never for one bad row (`tests/cron-define-guard.test.js`; its legacy list only shrinks). **A legacy cron with a `cron_heartbeats` row MUST call `stampHeartbeat(name)`** on success or it goes "stale" while running fine; only `health-check` and `ad-insights-backfill` have no stamp (manual-only backfill: no vercel.json entry, no heartbeat row — confirmed by the CRON-HB-AUDIT.1 audit, mig 406). **An ARM that rides another cron's schedule gets its OWN row** (`swap-cover-sweep` mig 623, name in `checklist-sweep/route.js`; `shift-reminders` + `roster-runway` mig 633, `shift-time-changes` mig 639, names + predicates in `src/lib/cron-arm-health.js`): stamped only when the arm returned an outcome with no fault of its own, under its own `.catch`, placed so the other arm cannot crash it out of its stamp — the parent's `last_outcome` pages nobody, since the health-check reads only `is_stale`. A run with nothing to send is healthy and stamps. Apply such a row's migration right AFTER the code deploys (or re-run it then): a row seeded early goes stale after interval + grace if the deploy is slower. **Changing a cron's `vercel.json` schedule re-sizes its row in the SAME PR** (a new migration; judge the live row, not the migration text): three schedule changes shipped without one and left `sync-class-occurrences` on a daily clock for a `*/15` cron for three months (CLASSSYNCHB.1, mig 644). Size the grace so ONE missed tick never pages: the gap between stamps is interval + Vercel jitter + run time.
- **Webhook handlers: idempotent, and return 200 for unrecognised events** (providers auto-disable hooks on non-2xx). High-volume webhooks defer (queue table + drain cron), never inline N writes. Long fan-outs run on cron, not the request thread.
- **A new Revolut-backed payment table needs a domain in `src/lib/revolut-reconcile.js`** (REVPAY.3, the `*/15` `revolut-reconcile` cron), applied through the SAME helpers its webhook uses, with a compare-and-set write, or a lost webhook leaves the customer's money taken and the row pending for ever.
- **A queued webhook event must NEVER be marked processed when it recorded nothing.** The dedup key is claimed at ingest, so the provider's own retry is already gone — reporting success after a no-op destroys the event permanently, in silence. POSTMARK-RACE.1: a Delivery landing 1-2s after the send API returned found no `email_sends` row (its `postmark_message_id` is minted by Postmark, so **write-first is impossible** and the row cannot exist until the batch call returns), logged, and returned ok — **3,231 of 10,191 Delivery events over 21 days, 100% of them lost**, one campaign reporting 4.8% delivery against ~100%. Fix the *lookup*, not the log: "no row" genuinely means both "ours, not committed yet" and "never ours" (655/21d of real ops-alert and host-campaign traffic), and **neither absence nor `Metadata`-presence nor a Tag allowlist separates them** — 277 noise events carry Metadata, 72 real ones carry none. Carry your own correlation id: `Metadata.crm_send` (`src/lib/postmark-send-marker.js`) is stamped at exactly the send sites that write an `email_sends` row, on exactly the condition each already gates its insert on. Marked + missing → return not-ok so the queue retries (bounded by `MAX_ATTEMPTS`, so it still dead-letters rather than looping); unmarked + missing → drop, and **not at `console.error`** — 31/day of ignorable noise at error level is what hid this. Answer QStash **200** for a retryable-miss (`deferred`), not 500: its retries fire inside the race window and would burn the budget before the row lands. POSTMARK-RACE.2 then fixed three things the first cut got wrong, all of the same shape — **a deferral is not free, so sizing it against the race window is only half the sum**: (1) *recovery must not inherit a queue* — handing every deferral to the `*/10` sweeper looked like a 45x margin but the sweeper's CEILING is `BATCH_SIZE`/tick (measured: exactly 100 per tick for 4+ hours on 10 Aug) against ~1,000 raced events per campaign burst, so a deferred row now re-publishes itself to QStash with `delaySeconds: 60` and an **attempt-scoped** dedup id (reusing the ingest id would be swallowed by QStash's dedup window and never delivered); (2) *a marker must carry a TIME* — `email_sends.contact_id` is `ON DELETE CASCADE` and contact erasure is routine, while Opens arrive up to 44 days late, so a constant marker read "a row was written" as "a row is coming" and dead-lettered erased-contact events under the false reason `send_row_not_yet_committed`; stamp `Date.now()` and defer only inside a 5-min window (unreadable marker → still defer, so the rule can only get stricter); (3) *replay makes a write idempotent-or-not that was neither before* — a deferred `Delivery` re-runs minutes later, after an `Open` may legitimately have advanced `email_sends.status`, so the timestamp and the status are written **separately**: `delivered_at` under the unchanged `.is('delivered_at', null)` transition guard (it is what makes the counter increment exactly once), `status` under `.eq('status','sent')` so the lattice never regresses.
- **The invoices inbound webhook processes a repeat delivery again, idempotently** (INVOICEPREP.1, `src/app/api/webhooks/invoices-inbound/[token]/route.js`). It claims `inbound-invoice:<MessageID>` first, and before this change a storage or insert failure answered 5xx and Postmark's retry was answered `deduped`: the invoice was gone. A held claim is no proof of storage either (a failed release or a run killed mid-ingest leaves it held), so the claim is now only an audit record and a hint: a delivery whose claim is already held is processed like the first one and answered with `deduped: true`. What makes that safe is the store: `ingestInboundEmail` (`src/lib/invoices-queue/ingest-email.js`) stores each attachment once per `email_message_id` and counts an attachment stored only once its `attachment_path` is written, and `recordInboundStray` is idempotent, so a true duplicate costs one select and adds nothing. Every non-2xx exit after the claim still calls `releaseWebhookEvent`. Mail that matches no studio is recorded in `invoice_inbound_strays` (masters see it on `/invoices`), not only logged. Once Postmark points at the shim, large mail arrives staged through `postmark-inbound-shim` (INVOICEPREP.2): the route reads the staged files with `resolveInboundAttachments` (`src/lib/invoices-queue/staged-attachments.js`) and removes them only after every attachment is stored. An attachment the function could not move becomes a row with `attachment_not_received: …`. The staged files of an email recorded as a stray (no studio matched) are kept under `inbound/` on purpose: for a mistyped address they are the only copy. Nothing sweeps them yet. Not covered: when Postmark is pointed straight at the Vercel URL, an email whose payload exceeds the platform's request-size limit is refused before the handler runs and is recorded nowhere. A webhook that claims before it writes needs both halves: release on failure, and writes a retry can repeat.
- **A new path that inserts into `invoices_queue` must hand the new row ids to `queueInvoicePreparation`** (INVOICEPREP.3, `src/lib/invoices-queue/queue-preparation.js`). Every row is read, checked and coded on arrival by `prepareInvoiceRow`, but only a row stamped with `analysis_queued_at` is ever claimed: the `process-invoice-analysis` sweeper (`claim_invoice_analysis_batch`, migration 872) takes `received` as well as `quality_approved` rows, and only stamped ones, and the QStash worker claims one by id on the same predicate. A path that forgets the call leaves its rows unread until a person clicks "Read again". The helper stamps the rows, publishes each id (a failed publish is logged and the sweeper covers it), never throws and never changes the caller's outcome; it leaves a live `analysis_claimed_at` alone, so a path that frees a claim must do so in its own write. A failed preparation keeps its claim and is retried once the claim is 10 minutes old. Preparation never sends anything to Xero: a send is always a person's click, and bulk send skips any row with `review_reasons`.
