# Data access and security

The full rules behind the one-line summaries in `CLAUDE.md`. Moved here word for word from `CLAUDE.md` on 19 Nov 2026 (CLAUDEMD.1); keep the two in step when a rule changes.

**Data access & security**
- **Service-role routes get NO RLS.** Every `/api` route uses `createServerClient()` (service role, RLS-bypassing). RLS only binds `authenticated`/`anon` — it does **nothing** for a route. Enforce access in app code: `assertLocationAccess(user, locationId)` for location rows, an org-membership filter for org rows, owner/recipient/master checks for per-user rows. Detail routes return **404 not 403** so IDs can't be enumerated. Audit any read route by asking "what filters this if I delete the RLS policy?" — if "nothing", it's an IDOR.
- **Integrations authenticate with a per-organisation `unitk_` API key ONLY** (APIKEYS.4; issued at `/settings/api-keys`, resolved by `authenticateApiKey`/`requireApiKeyOrManager` in `src/lib/api-auth.js`). There is no shared or global integration key any more, and never add one back: every org-scoping helper (`orgScopeLocationIds`, `assertRowInOrg`, `assertCreateInOrg`) no-ops on `orgId: null`, so an unscoped key reads and writes every tenant. Any other Bearer that is not a valid JWT falls through to the cookie gate and is refused; `src/proxy.test.js` and `src/lib/api-auth.test.js` pin that.
- **A GRANT/REVOKE binds the BROWSER's client, never a service-role path — and column-level `REVOKE` is silently ignored while a table-level GRANT exists.** Same blind spot as the bullet above, one layer down: `createServerClient()` is `service_role`, which bypasses column and table GRANTs exactly the way it bypasses RLS. So a locked-down column is locked only against `authenticated`/`anon`; a server page or route that `select('*')`s the table and hands the rows to a **client component ships precisely the columns the REVOKE exists to hide** — the rows travel in the RSC payload, and no grant, policy or linter is between them and devtools. Live on `/settings/staff` until STAFF-LIST-SCOPE.1 (#1599): `profiles` still carries `annual_salary`, `hourly_rate`, `contracted_hours_per_week`, `annual_leave_entitlement`, `overtime_rate`, and `settings` is held by **manager, owner AND master**, so every manager's browser held the estate's pay data on a page nobody reads as an HR surface. **Name your columns on any read that crosses into a client component**, and treat a table with a REVOKE in its history as one whose `*` is a leak. Second trap in the same story: **mig 153's column-level `REVOKE` did nothing** — Postgres drops it on the floor while the role holds table-level SELECT, which Supabase granted by default until mig 677 — and it took **mig 153b** revoking table SELECT outright to land. So verify a claimed lockdown against `information_schema.table_privileges` / `column_privileges`, never against the migration text; 153b self-checks that way for exactly this reason. Tables with column-level SELECT for `authenticated` (no table-level SELECT) include `rosters` (mig 618), `shift_blocks` + `shift_assignments` (mig 646, the coach projection the phone reads + `block_id`), `locations` (mig 648: the public identity + `organization_id`; **`settings` and every credential/config column withheld**; UPDATE only on LocationForm's and CarDepositSettings' columns), `contact_external_integrations` (mig 648, tokens withheld) and `email_sequences` (mig 654: `webhook_token`/`webhook_secret` withheld; `id`/`location_id` must stay granted because the `sequence_steps`/`sequence_enrollments` policies read them as the caller; no client write on any of the three, and the two children keep table-level SELECT because they hold no secret column); `profiles`, `channel_connections`, `whatsapp_numbers` and `xero_connections` have no client privilege at all (migs 153b, 648). A `locations` row read with `*` on the server carries six credentials: pass it through `redactLocationSecrets` (`src/lib/location-secrets.js`) before any client component or JSON sees it (`tests/location-secrets-to-client.test.js`). **A new column on a column-granted table needs an explicit grant decision**: until a migration grants it, every browser and phone is refused it, and a PostgREST select that names it fails WHOLE (42501, the phone's Today tab blanks), so the migration that adds it must `GRANT SELECT (<col>)` or say `-- column-grant: withheld <table>.<col>`. `tests/shift-column-grants-guard.test.js` enforces this for the two shift tables, checks every `shared/`/`mobile/` select on them, and fails a later migration that re-grants table-level SELECT on them (which would silently reopen every withheld column). `tests/credential-column-grants-guard.test.js` does the same for the five credential tables, and `tests/sequence-column-grants-guard.test.js` for the three sequence tables. Since mig 668 (GRANTSWEEP.1) `staff_attendance_events` has no client privilege and no policy (it used to show every studio member every colleague's door and geofence events, `payload` included; managers read it through `/api/attendance`), `shift_swap_requests` and `time_off_requests` are SELECT-only for `authenticated` (the swap INSERT policy let any member file a swap for a colleague's shift; every write goes through `/api/schedule/*`), and `anon` holds nothing on those three or the two shift tables. Since mig 676 (SHIFTCLIENTWRITE.1) `shift_blocks` and `shift_assignments` are read-only for signed-in sessions too: `authenticated` holds exactly mig 646's column SELECT list and nothing else, and the six manager write policies are gone (they let an owner, manager or head coach rewrite any shift or assignment at their studio, their own paid window and arrival stamp included, skipping the change log, the coach's push and the route's checks). Every shift write is server code on the service role: the `/api/schedule/*` routes, the geofence check-in (`/api/attendance/geofence-checkin`, the arrival stamp), the permanent staff delete (`/api/staff/[id]/permanent`, via `tombstone_staff_profile`), the staff assistant (`/api/assistant/chat`, via `upsertShiftAssignment`) and the nightly `/api/cron/extend-roster-horizon`; a new writer must be too (`tests/shift-client-writes-guard.test.js`). Since mig 679 (ROSTERCLIENTWRITE.1) `rosters` and `shift_templates` are read-only for signed-in sessions too: `authenticated` holds exactly mig 618's five-column SELECT on `rosters` and table-level SELECT on `shift_templates` (the phone's Today embeds read both), `anon` nothing, and the six manager write policies are gone (they let a manager or head coach approve an over-budget roster themselves, which the app reserves for owners, supersede or delete a published roster so its week vanished from every coach, and rewrite templates past the route's rules). Publishing, approving, rejecting and every template change is a service-role `/api/schedule/rosters*` or `/api/schedule/templates*` route (`tests/roster-client-writes-guard.test.js`). Never take a privilege off a column-granted table with a table-level `REVOKE SELECT`/`REVOKE ALL FROM authenticated`: it revokes that privilege on every column too, so revoke only the privileges you mean or re-grant the column list after it in the same file (`tests/scheduling-client-grants-guard.test.js` fails a later migration that does not). `audit_events` is service-role only (mig 655: no client grant, RLS on with no policy); the audit trigger masks secret-named keys (mig 647) and the exact PII keys in `private.audit_is_pii_key` / `AUDIT_PII_KEY_EXACT` (mig 655). Change a list in a new migration AND `src/lib/secret-keys.js`.
- **An OAuth-issued token (a Bearer JWT carrying `client_id`) opens `/api/mcp` ONLY, and every MCP tool lives in `src/lib/agent-tools/` declaring a gate and a studio** (MCP.1). `src/proxy.js` refuses that token on every other `/api` path, and `getCurrentUser()` refuses it everywhere, proxy-public routes included (MCPBEARER.1: only `getCurrentUserForMcp()`, called only by `verifyMcpToken`, accepts one; `tests/oauth-token-reach-guard.test.js`); the door (`verifyMcpToken`) refuses only a bad token, and the org switch, the `mcp_access` permission and the role are tool-level refusals. **`mcp_access` ("Connect an Agent", master+owner by default, bundled under `bundle_sales`; the SQL mirror is mig 826 — **written, apply before the code deploys**) is a SEPARATE key from `assistant` on purpose: the in-app assistant calls Anthropic on our key with NO spend ceiling, the MCP server calls no model at all, so they must be grantable apart** — MCP.1 shared the key and was therefore dead at every studio that had `features.assistant` switched off to stop token spend, and a refusal that names "AI Assistant" sends the operator to switch on the paid feature (MCPACCESS.1; the refusal code is `mcp_access_permission`). A tool runs on the service role, so it scopes itself: an optional `studio_id` resolved to a studio the person holds `mcp_access` at, a studio or contact-set filter on every query, named columns on `profiles`/`locations`/`contacts`. `tests/agent-tools-guard.test.js` fails a tool that skips any of it; the rest (dashboard steps, token reach, limits) is in `docs/architecture/INTEGRATIONS.md` § Staff MCP server.
- **MCP email tools PREPARE campaigns and can never RELEASE one** (MCPEMAIL.1). No `src/lib/agent-tools/` tool writes `campaigns.status` to `queued`/`scheduled` or is bridged to the assistant; a TOOL-prepared campaign is released only through `POST /api/communications/campaigns/approve/[token]` (session cookie, signed-in page, never an impersonated or support session), which calls `releaseCampaign` (`src/lib/campaign-release.js`); the CRM's own send/schedule routes also call `releaseCampaign`, for people. `tests/agent-tools-guard.test.js` (rule 6) pins it: no tool file names `releaseCampaign`/`consumeApproval` or writes a campaign `status` but `'draft'`. An approval (`campaign_release_approvals`, mig 830) is single-use, 24 h, bound to the person, the timing and the content key over the 16 `APPROVAL_CONTENT_FIELDS` (`src/lib/campaign-approval.js`; the last three are the resend's `resend_enabled`/`resend_wait_hours`/`resend_subject`: a resend to non-openers is approved WITH the first send and the `run-campaigns` cron creates and sends the child with no second approval, and a key change refuses an approval waiting at deploy once); a new `campaigns` column the sender reads must join that list (and `CAMPAIGN_COLS` and the approve view's columns, which the guard checks) in the same PR, or an edit after the test sends unapproved content. A/B tests, resends and non-`broadcast` campaigns are never released from an approval (`agentReleaseBlocker`). `update_email_draft` always returns the campaign to `draft` and voids approvals (the cron promotes `scheduled` with no approval check). `update_email_segment` refuses an edit when ANY sequence (any status) starts from the segment, and no tool deletes one; template reads (`list_email_templates`, `create_email_draft_from_template`) live in `src/lib/email-templates-for-agents.js`, outside `src/lib/agent-tools/` (MCPEMAIL.2). Never render agent bodies except through `src/lib/agent-email-blocks.js`; no agent HTML. Apply mig 830 before the deploy; detail in `docs/architecture/INTEGRATIONS.md` § Email campaigns.
- **Those same tool bodies have TWO doors, and a body must never ask a door's question** (ASSISTREG.2/.3, #2349). MCP's door is `runTool`: rate limit → `resolveStudio` (a studio the person holds `mcp_access` at) → the `org_settings.mcp_enabled` switch → one `mcp_tool_calls` row. The in-app assistant's is `src/lib/assistant/tool-bridge.js`: the web session, the studio is **ALWAYS `user.activeLocation`**, and `studio_id` is stripped from BOTH the advertised schema and the input, so neither the model nor anything steering it can name another studio. Both meet at `runToolAtStudio` (parse → ctx → the tool's own gate → run). Three rules, each already paid for: **`mcp_tool_calls` stays MCP-only** (assistant traffic in it destroys the only signal for whether anything has ever connected over MCP); **which studios a call may read contacts at is the DOOR's answer**, carried on `ctx.readableStudioIds` (`mcpReadableStudioIds` vs `assistantReadableStudioIds` in `_contact-scope.js`), and `readableContactStudios` is a pure read of it; **a door may add a floor but never a widening** (the assistant keeps its old role tiers as `TIER_FLOOR` under each tool's gate — a permission swap is only a tightening once you have read `DEFAULT_WEB_PERMISSIONS_BY_ROLE`). A new tool takes its studio and its contact reach from `ctx`, never from a permission it reads itself; `src/lib/assistant/tool-bridge.test.js` pins the boundary, stories in `docs/LESSONS.md`.
- **A new `public` function is executable by `service_role` only** (mig 667, FNEXECSWEEP.1). The default privileges no longer give EXECUTE to `PUBLIC`/`anon`/`authenticated`; `extensions` keeps the old PUBLIC default; `private`'s is `authenticated` + `service_role` since mig 678 (PRIVATEFNEXEC.1: RLS helpers need `authenticated`, and `anon`/`PUBLIC` execute nothing in `private`; a stored policy calls a helper by OID, skipping the schema check, so a PUBLIC helper ran for anon wherever anon reached the table; `tests/private-function-execute-guard.test.js`). A function a signed-in client calls (`supabase.rpc` from `mobile/`, `shared/`, a browser file, or champ-app's browser) needs `GRANT EXECUTE … TO authenticated` in the migration that creates it; every other new function states `REVOKE EXECUTE … FROM PUBLIC, anon, authenticated`. `DROP`+`CREATE` resets the ACL (`CREATE OR REPLACE` keeps it), and hand-made functions from the dashboard SQL editor start closed too; so does a function `postgres` creates in any NEW schema, because PUBLIC was revoked globally (re-grant per schema, as 667 does for `private`/`extensions`, if its callers need it). Trigger functions need neither, but an INVOKER trigger's *body* calls are checked as the firing role. `tests/function-execute-guard.test.js`.
- **A new `public` table, view or sequence is closed to every client session** (mig 677, TABLEDEFAULTACL.1). The default privileges for `postgres` in `public` now give tables, views and sequences to `postgres` + `service_role` only. `anon` holds nothing on any relation in `public` (nothing reads signed out: every public page, booking route and the widget read through `createServerClient()`), and `authenticated` holds no TRUNCATE/REFERENCES/TRIGGER/MAINTAIN and no sequence privilege anywhere (RLS does not apply to TRUNCATE). A table the phone, a browser file or champ-app reads directly needs `GRANT <named privileges> ON public.<t> TO authenticated` in the migration that creates it (never `ALL`); every other new relation states `REVOKE ALL ON public.<t> FROM anon, authenticated`. `DROP`+`CREATE` (a view too) resets to the closed default, and so does a table made by hand in the dashboard; `supabase_admin`'s own default, which `postgres` cannot change, still opens what IT creates. Prefer an identity column to `serial`/`bigserial`: a client-inserted table whose default calls `nextval()` also needs `GRANT USAGE ON SEQUENCE public.<seq> TO authenticated` in the same migration, or the first client INSERT fails with "permission denied for sequence". `tests/table-default-acl-guard.test.js`.
- **The user object from `getCurrentUser()` carries only `USER_PROFILE_COLUMNS` and `CLIENT_LOCATION_COLUMNS` (no location `settings`), and `user.user` is only `{ id, email }` of the auth user (`AUTH_USER_FIELDS`, AUTHUSERPICK.1); read anything else fresh by id** (`src/lib/user-profile.js`, PROFILESPREAD.1). It is serialised into every page, so a column added to it ships to every browser; `tests/user-profile-consumers.test.js` fails on a read of a dropped column (or of `settings`) off it.

- **A staff `profiles` row is NEVER deleted, and neither is its auth user.** `profiles.id → auth.users` is `ON DELETE CASCADE` (mig 004:36) and ~25 tables cascade off `profiles` (`shift_assignments`, `time_off_requests`, `staff_allowances`, `contractor_invoices`, `profile_compensation`, …), so either delete destroys payroll/leave/invoice history. Permanent delete is `public.tombstone_staff_profile()` (mig 622): the row stays with `deleted_at` set, PII stripped, `full_name` + pay kept, auth user **banned**, and only shifts that have **NOT STARTED** (each on its own studio's wall clock, from one `p_now` instant; mig 721, TZ.15) removed — a shift in progress or finished today is history. **RLS reads `profiles.role` LIVE** (`private.auth_is_master()`, `private.auth_role()`, dozens of inline `p.role = 'master'` policies — none checks `active` or `deleted_at`), so the function copies the role to `deleted_role` and demotes `role` to `'staff'`; role HISTORY is `roleAtDeletion()`, never `role`. A tombstone is always `active=false` + `role='staff'` (DB CHECK) with no `profile_locations`; any read that LISTS profiles without an id/active/email filter must go through `excludeTombstones()` (`src/lib/staff-tombstone.js`) — `tests/staff-tombstone-readers.test.js` fails on a new one. Never hand-list FKs into `profiles`: the old route's list covered 23 of 48 and named a dropped table. Three more locks, all in mig 622: a shift the person has **already arrived for** (`arrived_at`, or a matched `staff_attendance_events` row — arrivals match up to 45 min early) is history too; a tombstone is **frozen** by trigger (`deleted_*`, `role`, `active`, `email`, `permissions` can never change again, and `profile_locations`/`profile_organizations` refuse its id), and `anon`/`authenticated` hold **no write grant** on `profiles` — every profiles write is service-role, keep it that way. The login ban runs AFTER the SQL transaction: `auth_completed_at IS NULL` on a tombstone = half-finished, and `DELETE /api/staff/<id>/permanent` again re-runs only that step. **A data sweep that rewrites `role`, `permissions`, `email` or `active` for every profile (a migration backfill, a script) must filter `deleted_at IS NULL`** — the freeze trigger raises on the first tombstone and aborts the whole statement. **Keeping past shifts means a copy can re-roster the dead**: `bulkUpsertShiftAssignments` drops rows whose profile has no active membership at the target studio (`skipped_not_at_studio`) — any NEW bulk writer of `shift_assignments` must do the same.

- **A restrictive `FOR ALL` policy denies SELECT too.** RLS is (OR of permissive) AND (AND of restrictive), and `FOR ALL` includes SELECT — so the natural-looking `<x>_deny_writes ... AS RESTRICTIVE FOR ALL TO authenticated, anon USING (false)` does not deny *writes*, it denies **everything**, folding the table's own permissive SELECT away (`EXPLAIN` → `One-Time Filter: false`). It fails silently: reads return an **empty set, not an error**, and Supabase realtime — which authorises each `postgres_changes` row through the subscriber's SELECT policy — just never fires. Reached 16 tables and killed the Email/IG/Unified inbox listeners under a 60s poll. Write denial goes per-command (`FOR INSERT` + `FOR UPDATE` + `FOR DELETE`), keeping a `FOR ALL TO anon` backstop if anon must stay shut out. Migs 483, 485; `check:rls-restrictive` now gates it.
- **One permissive policy per (table, command).** Don't pair a `FOR ALL` "manage" policy with a separate read policy — the `FOR ALL` overlaps the read on SELECT and trips `multiple_permissive_policies` (counted ×5 grant roles). Instead write the manage side as **explicit `INSERT`/`UPDATE`/`DELETE`** policies and keep a **single `SELECT`** policy whose `USING` is the OR of every population that may read. RLS ORs permissive policies, so `FOR ALL` ≡ the four per-command policies and merging reads is behaviour-preserving. Scope policies `TO authenticated` unless anon genuinely needs them.
