# Conventions that bite

The full rules behind the one-line summaries in `CLAUDE.md`. Moved here word for word from `CLAUDE.md` on 19 Nov 2026 (CLAUDEMD.1); keep the two in step when a rule changes.

**Conventions that bite**
- **No silent env fallbacks** (`getAppUrl()` throws if unset) and **no `x-api-key`** — Bearer or session only. Standard response shape `{ success, data?, error?, issues? }`.
- **Consent has two families:** `_administrative` (transactional/reminders) vs `_marketing` (broadcasts). Reminders check `_administrative`; MARKETING WhatsApp templates are refused on transactional paths (Meta policy). Both live in `contact_preferences` (per-studio marketing in `contact_location_preferences`) and every change is recorded in `consent_log`; since mig 660 (CONSENTCLIENTWRITE.1) no client session writes them, and since mig 662 (CONSENTREAD.1) none **reads** them either: `anon`/`authenticated` hold no privilege on the three tables or on `contact_location_audience`, RLS is on with no policy. `contact_preferences.unsubscribe_token` is the credential behind the public preference centre, so a route that shows consent to staff returns the flags and history it needs, never the token (`tests/consent-tables-client-closed-guard.test.js`). Re-creating `contact_location_audience` must keep `WITH (security_invoker = on)` and then `REVOKE ALL … FROM anon, authenticated, PUBLIC` before restoring its ACL from the catalog (the mig 652 pattern), because before mig 677 a `DROP`+`CREATE` silently re-granted `anon`/`authenticated` through the schema's default privileges (keep the REVOKE: it is still right on a database whose defaults were reset). A consent change goes through a service-role route that writes `consent_log` in the same request (`/api/contacts/[id]/marketing-preferences`, `/api/contacts/[id]/studio-consent`, `/api/preferences/[token]`, `/api/unsubscribe/[token]`, `marketing-consent.js`, `whatsapp-consent.js`); the DEFINER mirror triggers copy it onto `contacts`. A change to ONE studio's list (the preference centre's `locationId` path, and staff's per-studio switch with its required reason on `consent_log.reason`/`note`, STAFFCONSENT.1, mig 831) goes through `applyStudioPreferenceChange` (`src/lib/studio-consent.js`), which writes that studio's row only, never `contact_preferences`. STOP/START on WhatsApp write the thread studio's `contact_location_preferences` row only (WAORGNUMBER.3); a contact-wide WhatsApp opt-out (Meta's own preference, or a keyword with no studio) also sets every studio row false; Meta's preference stays contact-wide within the organisation. Since mig 747 `sync_contact_location_preferences` acts only on channels that CHANGED (INSERT mirrors all), so a studio STOP/START is never undone by an unrelated `contact_preferences` write. `tests/consent-tables-client-writes-guard.test.js` fails a client writer and a later migration that reopens one.
- **An UNREGISTERED `sendPush` category fails CLOSED, not open.** `resolvePermission`'s last tier is `defaults[role][key] === true`, so `notify_<madeUpCategory>` resolves **false** for every role but `master` (which bypasses the tiers) — the push reaches the person who tested it and silently nobody else. Either register the key in `MOBILE_PERMISSIONS` + `DEFAULT_MOBILE_PERMISSIONS_BY_ROLE`, or send **categoryless** (master switch + device permission still gate) and route Android via `data.type`. Categoryless is right for operational notices that aren't a preference. Bit `app_update` (STAFF-DEV.8) and `test` (PUSH-TEST.1) within a day of each other. **And `category` is the BARE name — `resolvePushAllowedIds` prepends `notify_` itself**, so passing the permission KEY (`category: 'notify_inspection_due'`) gates on `notify_notify_…`, which is this same unregistered class: all three equipment pushes reached masters only from EQUIP-MAINT.3 until PUSHCAT.1, under route tests that asserted the prefixed literal. The `sale` category (SALEALERT.1) is the one staff push that rings at any hour, by the owner's choice: it never calls `inStaffPushHours`; `notify_sale` is offered only to master/owner/manager (`onlyRoles` + `permissionOfferedToRole`, display only). **What rings a `sale` push (SALEALERT.1):** a new sale only, through `notifyNewSale` (`src/lib/sale-alert.js`), to owners and managers at the sale's studio and nobody wider. It does NOT ring for renewals, refunds, an amount not above EUR 0, fees and recovered arrears, donations, a raffle, car deposits, an entry paid to a host's own Stripe account, `move_gap` payments, or an event with no `location_id`. The dedup key is `sale:<source>:<saleId>` (sources `offer`, `trial`, `class_booking`, `pay_link`, `race`, `glofox`, `un1t`) in `push_event_sends`, so a webhook retry or a second path rings once; any sale paid on the un1t.online rail uses the shared key `sale:un1t:<remote transaction id>` whichever path sees it first. A route handler hands the alert to `ringSaleAfterResponse` so it never delays or fails the payment answer; `notifyNewSale` itself never throws. The Glofox filter (`glofox-sale-alert.js`: paid, above EUR 0, not complimentary, every line-item sub-type on the allow-list) and the un1t.online filter (`un1t-sale-alert.js`: type `one_time` or `sub_initial`, not refunded, above EUR 0) are ALLOW-LISTS: a type nobody has seen yet stays silent until someone adds it on purpose. Reason: a wrong ring teaches the owner to ignore the push, and a renewal or fee ringing as a sale hides the real ones. Guard: the unit tests beside each adapter and `tests/push-category-literals.test.js`. `tests/push-category-literals.test.js` scans for the prefix and requires every registered `notify_<category>` to have a `CATEGORY_CHANNELS` entry.
- **Stillorgan's three pipeline boards are placed by ONE router, and the €39 trial's credits are never a Class Pack** (PIPE3, migs 797/798). `routeContact()` in `shared/pipelines/router.js` decides a contact's board (Cold/Gympass pile → live paid claim → live programme claim → `classifyContact()`); the nightly `pipeline-reclassify`, `ensureDealForContact` (webhook, Cold route, `placeContactNow`) all call it, and a new placement path must too: a path that calls `classifyContact()` on its own for PLACEMENT is PIPELINE-FLAP in a new costume. A deal follows the person across boards (`pipeline_id` + `stage_id` in one update, never close-and-recreate). An unreadable claims read (`trial_purchases`, `pipeline_board_claims`, `locations.settings`) places NOBODY that run — never "no claims", which would move every buyer back. `shouldStampPackCustomer` refuses while a paid claim is live (the 14 Day Reset is 10 credits; the old rule filed buyers in Class Pack), and on the €39 board a pack is Converted only from the trial's END. The programme match is recorded in `pipeline_board_claims` (Glofox overwrites the plan name on every sync); the rules are `locations.settings.pipelines.programmes`, never a hard-coded `meta_50plus`. The new slugs are audience-filterable; only the €39 board's moves start `pipeline_stage_change` sequences from the nightly pass (STILL39SEQ.1, `CONTACTS_STAGE_TRIGGER_MODULES` in `src/lib/pipeline-reclassify.js`: its Day 7 and Trial Done are reached by time), and a Stillorgan purchase is greeted by the `paid_trial_checkout_purchased` trigger (`src/lib/trial-checkout-purchase-sweep.js`), never by Hatch's un1t one. `docs/architecture/REFERENCE.md` § PIPE3. **At a un1t.online studio (Hatch) the same router runs off the mirror (HATCH39, migs 803/804): a paid-trial product (`paidTrialProductIdsFor`, `src/lib/paid-trial-products.js`; un1t.online sells the €39 trial as a `pack`) is never a pack on ANY read (snapshot, eligibility, dashboard counts, Churn Radar, trial-done) and is judged by the amount PAID, never the product's current price (a €0 transaction on it is the free trial it used to be: PAIDTRIALAMOUNT.1), a failed read of the set throws rather than answering "no paid trials", and `ensureDealForContact` never places at a studio whose primary board's module has `inputSource 'un1t_online'` (the hourly un1t pass is the one writer). The Waitlist board is retired (1 Nov 2026), never deleted.** § HATCH39.
- **`contacts.wa_phone` is derived from `phone` by ONE rule in two twins** (WAPHONE.1, mig 753): the trigger `derive_wa_phone` → `public.normalize_wa_phone` on every contacts INSERT/UPDATE OF phone, and `waPhoneFromPhone`/`contactWhatsAppNumber` in `src/lib/phone-validate.js` for code that needs the number before a write. Change both in one PR (`tests/wa-phone-normaliser-parity.test.js` runs both over `tests/helpers/wa-phone-cases.js`). Stored form is E.164 digits, no `+`. Never write a raw or `toE164Ireland` phone into `wa_phone`; a wa_phone that differs from the phone's derivation (learned inbound) is never overwritten.
- **An inbound WhatsApp message may carry NO phone number** (WA-BSUID.2). A sender with a username can hide it: Meta omits `messages[].from` and `contacts[].wa_id` and names them by a business-scoped user id (`from_user_id`, `IE.1349…`). Read the sender through `inboundSender()` and address a thread's reply with `conversationAddress()` (`src/lib/whatsapp-address.js`), never `message.from` or `conversation.wa_phone` raw: the send functions turn a BSUID into Meta's `recipient` field (`recipientFields`). A BSUID is never a phone: never strip it to digits or match it against phone columns (`isBsuid`). The webhook handles each message and each status in its own try/catch, because one throw used to skip the rest of the delivery. **The stored messaging limit (`whatsapp_numbers.messaging_limit_tier`) is read from Meta's `whatsapp_business_manager_messaging_limit`** (WA-LIMIT.1; the old field stopped coming back), always through `normalizeMessagingLimit`, and "Meta did not say" keeps the last known tier: a NULL tier switches the blast/drip budget gate off.
- **An unpaid /trial checkout is followed up by ONE sweep, and "could not read" there is never "did not buy"** (TRIALABANDON.1, migs 835/836). `sweepAbandonedTrialCheckouts` (`src/lib/trial-checkout-abandoned.js`, an arm of `process-trial-purchases`) enrols into `paid_trial_checkout_abandoned` sequences and exits anyone who has since paid (`exit_reason 'trial_purchased'`); what counts as a purchase is `isPurchaseRow` / `PURCHASE_ROW_FILTER` in `src/lib/trial-abandoned-purchase.js` (change both together), plus the un1t.online mirror at a un1t.online studio. A failed eligibility read holds that person unstamped; every other outcome stamps `trial_purchases.abandon_followup_at`/`_outcome` after the enrolment. The enrolment is MARKETING (never add its source type to `TRANSACTIONAL_SOURCE_TYPES`). `docs/architecture/REFERENCE.md` § TRIALABANDON.1.
- **A `class_booking_requests` row with `funded_by` set (CLASSFIRST.1, mig 799) is a class a /trial buyer or a /corp claimant picked and already holds credits for: the processors never grant a trial for it, and an empty balance is a `funded_no_balance` card, never the paid-trial reply.** Every grant path that books a chosen class goes through `queueFundedClassBooking` (`src/lib/class-first-booking.js`), best-effort after the grant stamp; a new grant path does the same, never its own insert.
- **`trial_purchases.attribution` holds the buyer's IP address and user agent (`client_ip`, `client_user_agent`) from checkout until the Meta Purchase is sent** (HATCHTRACK.1, `src/lib/trial-purchase-conversion.js`): only the Purchase reads them, and they leave the row in the SAME write that marks it granted, failed or expired (`clientDataRemoval`), never in a later whole-object write of `attribution` (the follow-ups stamp `meta_*_sent_at` into it once a row is granted, and a stale copy written back would erase a stamp). Never return `attribution` from a public route or hand a `select('*')` of the table to a client component (the public status route names its columns and its test pins that). A Hatch Street (un1t.online) row is ONE purchase however many checkouts it was given: **Continue to payment** (`POST /api/public/trial-purchases/[id]/checkout`, `src/lib/trial-purchase-un1t-resume.js`) mints a fresh checkout for the same row and never changes its status, and only after `un1tRetryGate` passes (still awaiting payment, newest checkout minted with the `paid=1` return, no payment in the mirror, nothing on un1t.online's live credits ledger; a failed read is never "unpaid": a second un1t.online payment settles no row and needs a refund by hand), and the settle sweep expires a row off its NEWEST checkout on the write ledger, so a new path that gives a row a checkout must go through `createCheckoutLink` with `originRef` = the purchase id.
- **Customer-facing copy/labels must be operator-editable** (settings field + default fallback), not hard-coded.
- **A multipart POST to any `/api` route is capped at ~4.5MB by Vercel, and the rejection is a PLAIN-TEXT 413** that fires before the route runs — so a route-side size cap above that is unreachable, and a bare `res.json()` on the client turns it into `Unexpected token 'R'…`. Every browser uploader sends `compressImageForUpload()`'s output (images) and parses with `parseUploadResponse()` — both in `src/lib/landing-media-upload.js`; files that must stay big (video) go direct-to-Storage via a signed URL (`…/media/signed-upload`). Bit the landing editor first, then the event hero forms (HEROUP.1) which hadn't adopted the helpers. A signed upload (`createSignedUploadUrl` in a service-role route, `uploadToSignedUrl` in the browser) is authorised by its token, not by RLS: the Storage API runs it as superuser, so it needs **no** `storage.objects` policy, and a bucket written that way should have none for `authenticated`. Mig 670 (WATPLBUCKET.1) dropped the ones on the public `whatsapp-templates` bucket (any session could upload any file there) and gave it the template-media size/MIME limits. RLS is skipped but the bucket's `file_size_limit` and `allowed_mime_types` **still apply to a signed upload** (itself capped by the project-wide upload limit), so a change to `TEMPLATE_MEDIA_LIMITS` in `src/lib/template-media.js` needs a matching bucket migration in the same PR, or Storage refuses the new type or size at upload time; `tests/whatsapp-templates-bucket-guard.test.js` enforces it. Mig 671 (TVBUCKET.1) closed the same hole on the public `tv-content` bucket, which only the service-role `/api/admin/tv-displays/upload` route writes: its limits are `src/lib/tv-media.js`, the constants that route validates with, and `tests/tv-content-bucket-guard.test.js` keeps route, constants and bucket in step. Mig 675 (BRANDINGBUCKET.1) dropped the three `private.is_owner()` policies on the public `branding` bucket: `is_owner()` is owner or master ANYWHERE, so an owner at one studio could upload into any studio's logos, landing-page and event media straight from their own session, past every route's per-studio gate and file checks (and one SELECT policy would have let them overwrite and delete too). The bucket is written only by the service-role routes that gate on the file's studio or event, and by the landing editor's signed video upload; its limits are `src/lib/branding-media.js`, and `tests/branding-bucket-guard.test.js` fails a client write, a policy that admits the bucket, a new unreviewed writer, and a writer that accepts a type or size the bucket refuses. Mig 869 (GIFLIB.1) added `image/gif` to the bucket and to `/api/landing-page-settings/media`, so an animated image can sit in a studio's library for the email tools; the browser uploader never compresses a GIF (a canvas keeps only its first frame). Mig 687 (CARDOCBUCKET.1) gave the private `car-documents` bucket (car documents and the saved Xero sales-invoice PDFs under `cars/`; closed to clients by mig 403) the limits of `src/lib/car-document-media.js`: 25 MiB and seven types (PDF, JPEG, PNG, GIF, WebP, HEIC, HEIF). `POST /api/cars/[id]/documents` refuses anything else with a 400 and judges an unlabelled file by its bytes, and `tests/car-documents-bucket-guard.test.js` keeps the route, the picker, the Xero PDF writer and the bucket in step. Since CARDOCUPLOAD.1 the web picker never posts the file: it signs (`…/documents/sign`, which also decides the type to upload AS, since the bucket's `allowed_mime_types` would refuse an unlabelled file or an alias sent as itself), uploads with `uploadToSignedUrl`, then `…/documents/finalise` re-judges what Storage holds and records it (`src/lib/car-document-upload*.js`).
- **Branding lives on `company_settings`** (`logo_url`/`favicon_url`/`company_name`, one row per `location_id`) — resolve via `getLocationBranding(db, locationId)`. There is **no `company_branding` table** (just the mig 013 *filename*) and `locations` has no branding columns; either wrong source silently renders no logo (bit both contract + invoice emails).
- **Background watchers must NEVER `git checkout`/`pull`** (shared worktree — raced foreground once). Read-only `git log`/`gh` only.
- **In a component test, move the fake clock INSIDE `act()`** — `await act(async () => { await vi.advanceTimersByTimeAsync(ms) })`. `vi.useFakeTimers()` does not fake the clock React renders on (its Scheduler captured the real `setImmediate`/`performance` at import), so a bare advance followed by `getBy*` is a fixed hop count racing a real-time render, and it loses on a loaded runner: one test of 26,023 cost a merge its OTA (2026-09-20). Never "fix" it with a longer wait or a second `advance(0)`, and `findBy*`/`waitFor` only work under a fake clock installed with `{ shouldAdvanceTime: true }` (otherwise RTL awaits a faked `setTimeout(0)` and hangs to the 5000ms budget) — which leaks REAL elapsed time into the fake clock, so it is wrong for any test that counts debounced calls. `tests/fake-timer-act.test.js` enforces it; story in `docs/LESSONS.md`.
- **New tests that need a database use `createFakeDb` (`tests/helpers/fake-db.js`), not a hand-rolled fake.** It is checked against `supabase/schema/snapshot.json`: an unknown table, column, function or argument throws, and it keeps PostgREST's 1,000-row cap, NULL rules, `.single()` errors, NOT NULL failures and ambiguous-embed refusal.
- **`tests/role-access.test.js` runs the live access rules on real Postgres as each kind of session** (`tests/helpers/role-db.js`, rules captured in `supabase/schema/access.json`). A migration that changes a policy, grant or RLS helper refreshes that file with the snapshot (`supabase/schema/snapshot-queries.sql`, `scripts/schema-access-build.mjs`); add a case for a table the phone or browser reads directly.
- **Await every async assertion.** `expect(p).resolves…`/`.rejects…` and `expect.poll(…)` return a promise; one that nothing waits for lets the test end first, so it passes without checking or fails a LATER test (#1762 lost a CI run to one). Write `await expect(…)`. Under fake timers, attach first and await after the clock moves: `const settled = expect(p).rejects.toThrow(…); await vi.advanceTimersByTimeAsync(ms); await settled`. **Lint-enforced** by `guardrails/no-unawaited-async-expect`, in `check:guardrails` (test files and helpers under `src/`, `shared/`, `tests/`) and `check:mobile-lint` (`mobile/**/*.test.js`). A `return` or a concise arrow counts as waiting; a `return` inside `.forEach` does not. **Blind spot:** an assertion inside a callback or helper whose OWN promise floats — `forEach(async …)`, an un-awaited `.map(…)`, an async IIFE, a helper that returns the assertion called without `await`. It can also flag correct code that passes the assertion as an argument or stores it in an array/object: bind it to a `const` and `await` that. The rule is a floor, not proof.
- **Mia stays on the Anthropic Messages API** (not the Agent SDK); **no OpenAI** anywhere (Richard's call — incl. voice transcription).
- **Mia states an offer's price, end date and link only from `list_current_offers`** (MIAPAGES.1, `src/lib/agent/offer-tools.js`). The tool reads every live landing page and every sellable `/offers` storefront offer in the conversation's organisation, live, through `readCurrentOffers` (`src/lib/agent/offer-read.js`), with the same "can this be sold now" checks the public pages use (the trial entry, the promo row, the Open Week window, the storefront's own rules, stock). Nothing is copied into the knowledge notes, so nothing goes stale. **A new public surface that sells or gives something is added to `readCurrentOffers`**, or Mia will not know it exists. Pages reach her ranked (`rankPages` in `offer-view.js`): an offer with an end date leads while it runs, then the open-ended trial leads again; `chrome.mia_priority` on a page (`lead` / `ask_only`, set in the page editor) overrides that, and `chrome.mia_note` says who the page is for. Nothing internal is in the result (no promo key, plan code, product or offer id, stock number), and a failed read is "unreadable", never "no offers". The un1t.online prompts are tested never to contain the word "limited", so the stock flag is `while_stocks_last`.
- **A past event's raffle or donation link reaches Mia only through `still_giving`** (MIAGIVING.1, `src/lib/agent/event-giving.js`). `list_upcoming_events` reads future events at the conversation's own studio; `readStillGiving` adds the past UN1T events (no host, active, published, charity switched on, because the public page shows no raffle or donate card without it) across the conversation's organisation whose raffle sells online right now (`onlineSalesState`) or whose date is within `GIVING_WINDOW_DAYS` (30). A donation page never closes by itself, so that window is the only end it has for Mia. An event dated today counts too, unless it is already in the upcoming list; a past event is listed only once its sign-up is closed (`charity.signup_off` or a past `registration_closes_at`), because the public page judges sign-up by its times alone and would offer a paid entry to an event that has happened. Each entry is a name, studio, date, charity, what is open, the raffle's closing label and the event page link: never a total, a ticket number or an id. A failed read sets `still_giving_unreadable`, never an empty list. Upcoming events, bookings, cancellations and moves stay scoped to the conversation's studio.
- **Mia says about an event only what `list_upcoming_events` gives her** (MIAEVENTFACTS.1, `EVENT_FACTS_RULE` in `src/lib/agent/prompt.js`). Given only "a raffle is open" she told a customer the raffle entry came with registration, which was made up. Every event in the result, upcoming or in `still_giving`, now carries what its own public page shows: the description up to `MAX_EVENT_DESCRIPTION` (1,500) characters, and for a charity event the charity, `donations_open` and, while the raffle sells online, `raffle_tickets` (the ticket prices as the card sells them, `raffleTicketLabels`) and `raffle_closes_label` (`givingDetails`, `src/lib/agent/event-giving.js`). For anything the result does not answer she says she does not have that detail and sends the event's link. **A new thing an event page shows is added to that result**, or Mia will not know it and must not guess. A failed raffle read on upcoming events sets `raffles_unreadable`, never "no raffle". KNOWLEDGE about an event by name may be used too, and the tool wins where they disagree; a missing event detail is answered with the link, not a handoff. `still_giving` also lists a charity event that is still to come when the upcoming list does not carry it (another studio's, or one whose sign-up is closed or switched off), with `when` saying past, today or upcoming. A charity event with `charity.signup_off` is never offered as something to enter and `book_event` refuses it, as the public page and register route do. The upcoming read takes published events only, and a failed read answers `events_unreadable`, never "nothing on". The raffle and donations are part of the event (Richard, 23 Nov 2026): someone asking about an event is told what is open for it, with the ticket prices and the link, whether or not they named the raffle; they are left out only when the conversation is not about that event. A tool result is not kept between messages, so the rule and the tool description both tell Mia to call `list_upcoming_events` again before every answer about an event (MIAEVENTREREAD.1): asked "what was done for charity?" one message after sending the link, she answered "I don't have the details" without calling it, while the description held the answer.
- **Mia's history carries the date of every earlier-day message** (MIAHISTORYDATES.1, `formatHistoryForClaude` in `src/lib/agent/core.js`). A class reminder says "tomorrow"; with no date on it, yesterday's reminder read as today's and Mia offered a member a class that had already happened. With `opts.zone` (the customer reply, the follow-ups and the approval suggestion all pass the studio's), a conversation that reaches back before today has every message stamped on the studio's clock: `[sent Sun 22 Nov]` for an earlier day (with the year when it is not this one), `[sent today]` for today's, so two reminders merged into one turn are still told apart line by line. A conversation that is all today carries no stamps. The stamp is ours alone: `sanitizeInboundText` takes the brackets off a customer's own, and `parseAgentResponse` cuts one the model copies to the start of a line in a reply. `HISTORY_DATES_RULE` explains it and tells Mia to read a member's bookings with her tools before naming or changing them, never from an earlier message or reminder. A new caller of the formatter that wants dates passes the zone.
- **A class described once is known at every studio, and nothing else crosses** (MIACLASSNOTES.1, `src/lib/agent/shared-class-notes.js`). Class descriptions are knowledge notes imported per studio from the Glofox timetable; a studio that is not on Glofox gets none, so at Hatch Street "What's RECLA1M?" was a hand-off while Stillorgan held the answer. The customer reply's knowledge read (`readAgentKnowledge` with `shareClassNotes`) now adds a sibling studio's note when it describes a class on this studio's own timetable (`un1t_events`, matched by `classKey`: "RECLA1M. - CONDITIONING" is "RECLA1M") and this studio has no note of its own for that class, enabled or not. A sibling's offers, prices, billing or hours are not on a timetable, so they never match. Siblings are the active, non-host-anchor studios of the same organisation. The borrow is additive: a failed read adds nothing and the studio's own notes still answer. To give a studio its own wording, add a note there with the class name as its title.

## Coding conventions

Full set in [`docs/architecture/REFERENCE.md`](docs/architecture/REFERENCE.md); the high-frequency ones:

- **UI primitives** live in `src/components/ui/` (`Button`/`Modal`/`Card`/`Field`/`Table` from `@/components/ui`); compose them, don't re-roll. Colours use intent-named `un1t-*` tokens on a **light theme**: `bg`/`surface`/`border`/`muted`/`subtle`/`text`/`accent` (full hex table in `docs/architecture/REFERENCE.md`). The names were inverted (`un1t-black` held white) until UI-FOUND.1 **deleted** them — an old name is not an alias, it emits **no css at all**, so the element silently inherits and nothing errors. 198 of them were still being written into new features weeks later because this file and REFERENCE.md still documented the old names; the tell was an operator asking what belonged in the black box on `/offer-sales`. `no-dead-un1t-token` (`check:guardrails`, repo-wide + mobile) now blocks them, and `--fix` does the rename. **Status chips: `bg-<c>-500/10 text-<c>-700`** — text on light cards needs the -700 ramp, never -300/-400, and never the dark-theme recipe (`bg-*-900` + low ramp; the unreadable green-on-green credits pill, operator-reported 2026-07-03). Lint-enforced via `check:guardrails` (`no-low-contrast-chip`); genuinely dark surfaces (TV/present) are path-excluded in `eslint.guardrails.config.mjs`. **The chip rule only inspects the bg+text PAIRING**, so plain accent text with no chip background was invisible to it — 52 shipped that way across the six Communications editors. `no-low-contrast-accent-text` covers that half: any `text-<palette>-300/400/500` with no `bg-black` on the same element. It is **armed per-path**, not repo-wide (it cannot see the rendered surface, and ~500 low-ramp sites elsewhere include correct dark-surface idiom) — the armed list in `eslint.guardrails.config.mjs` is currently the Communications area; **clean an area, then add its path, one line**. A genuine dark island inside a light page keeps its low ramp by putting `bg-black` on the *same* element, not by a disable comment.
- **A new route is `export const POST = withAuth({ … }, async ({ user, db, locationId, input, params }) => …)`** (`src/lib/with-auth.js`, ROUTEWRAP.1): it does the sign-in, permission, role, studio and schema checks and catches a throw as a fixed 500. For a studio in the URL use `location: 'param'` (a non-member gets 404, and the permission and `roles` are judged AT that studio, masters passing); `master: true`, `allow(user, locationId)` and `forbiddenMessage` cover the rest. `tests/route-wrapper-guard.test.js` requires it (its legacy list only shrinks). `src/lib/openapi.js` documents only the API-key routes (RETIRE.2): register a route there when it takes a `unitk_` key.
- **Reuse shared Zod blocks** from `@/lib/schemas` (`uuidLike` — Postgres-permissive, NOT `z.string().uuid()`). **Not style: zod 4's `.uuid()` is RFC-strict and REJECTS UN1T Stillorgan's seeded id `a0000000-0000-0000-0000-000000000001`** (version nibble 0) — the only id in the estate that fails it, and the flagship. All 18 MCP tools declared `studio_id: z.string().uuid()`, so naming that studio answered `invalid_input` while omitting `studio_id` worked (MCPACCESS.2, #2348; `tests/agent-tools-guard.test.js` now REQUIRES `uuidLike`).
- **No new `console.log` in prod paths** (gate on `NODE_ENV` or use `console.error`).
- **Fire-and-forget side effects** (confirmation email/push after a write) run in their own `try/catch` and never block/fail the primary response; the helper swallows its own errors. Multi-channel sends run channels independently (email-down ≠ push-down); partial send counts as `sent`.
- **Deprecated columns stay on disk** — new migration adds + backfills, `COMMENT ... 'DEPRECATED (mig N)'`, code stops reading/writing, a *later* migration drops. Lets code roll back without DB action.
- **zsh + bracketed paths:** `[id]`/`[slug]` are globs — single-quote or `noglob` git commands or staging silently empties. Stale `.git/*.lock` from an IDE: `find .git -name '*.lock' -delete`, then quit the IDE.
