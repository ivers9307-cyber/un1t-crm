# supabase-js and PostgREST traps

The full rules behind the one-line summaries in `CLAUDE.md`. Moved here word for word from `CLAUDE.md` on 19 Nov 2026 (CLAUDEMD.1); keep the two in step when a rule changes.

**supabase-js / PostgREST traps** (these fail *silently*)
- **Builders are thenables, not Promises** — they have `.then` but no `.catch`. `await db.rpc(...).catch(()=>{})` throws and the rpc never runs. Use `try { await … } catch {}`.
- **`.update()/.insert()` must be `await`ed** or the request never fires (silent no-op).
- **`auth.signOut()` deletes the PKCE code verifier** (`_removeSession()` drops `${storageKey}`, `-user` AND `-code-verifier`, for every scope but `'others'`, even with no session). Never sign out on the path to `exchangeCodeForSession()` — establish the session first, sign out only on failure. Recovery/invite links go through `src/lib/recovery-link.js`; also parse `error_code` off the callback URL (an expired link is not a malformed one).
- **1,000-row select cap.** Every `.select()` returns ≤1000 rows regardless of `.limit()`. Any fan-out (sends, imports, backfills) must `.range()`-paginate with an explicit `.order()`. Copy `src/lib/pipeline-reclassify.js`.
- **A backfill queue needs a cursor that advances on EVERY attempt.** Ordering candidates by a "still missing" flag lets rows that legitimately stay missing fill every page forever: the Glofox detail backfill ordered `plan IS NULL` first under the 1k cap and re-read the same 2,926 no-plan contacts every ~30 min (~288k Glofox calls a day) while 2,917 others went unrefreshed from July (DETAILBACKFILL.1). Stamp a due/attempted column whatever the answer (a refusal and a 404 included), order by it, and keep the per-tick page under 1,000. Never reuse another job's timestamp as the cursor (`glofox_synced_at` is the attendance refresh's).
- **Bare `contacts(...)` embeds 300 (`PGRST201`) once a table has ≥2 FKs to contacts** — disambiguate `contacts!contact_id(...)`. ≥2-FK tables today: `whatsapp_conversations`, `instagram_conversations`, `team_members`.
- **Embedded-resource filters break under count-only (`head:true`) selects** → return 0, no error. Don't fight it: denormalise the filtered column onto `contacts` via trigger (that's why `contacts.email_marketing` / `pipeline_stage_slug` exist).
- **`.select()` options (`head`/`count`) are only read on the FIRST `.select()` after `.from()`** — a `.select()` chained after a filter silently ignores them.
- **`.ilike(col, value)` is a PATTERN match, not a case-insensitive `=`.** `_` and `%` are LIKE wildcards *and* legal email characters that `normalizeEmail` accepts, so `a_b@x.com` also matches `axb@x.com` and `%@x.com` matches the whole domain — on the inbound-email webhook the sender is attacker-controlled, so this let a stranger's mail be filed against a real contact, silently. For an **equality** check wrap the value in `escapeLikePattern()` (`src/lib/like-escape.js`); **not** `.eq()`, since contacts are stored mixed-case. `.maybeSingle()`/`.limit(2)` are not guards — they catch the >1-row case, but a `_` matching exactly one *wrong* row returns it happily. Deliberate substring searches spell their wildcards in the source (`` `%${term}%` ``); `check:guardrails` (`no-unescaped-ilike-pattern`) enforces the split. Beware too that supabase **mocks** model `.ilike` as `lower(a)===lower(b)`, which is why this passed CI for months — use `ilikeMatches` from `like-escape.test-helpers.js`.
- **`const { data } = await …single()` is a silent no-op waiting to happen.** `.single()` errors whenever the row count is anything but *exactly one*, so discarding the error collapses **"no rows", "many rows" and "the query failed"** into the same `data = null`. Live twice on 2026-08-11: `PUT` (#1357) and `POST` (DEALSCOPE.2) `/api/deals` both resolved a stage with `.eq('slug', …).single()` — every core slug exists on **five** locations, so the query matched 5 rows, errored, and the caller got a success with the deal unmoved / created stageless. **Lint-enforced via `check:guardrails` (`no-discarded-single-error`)**, which flags a `.single()` destructured without `error` *unless* the chain pins the **primary key** (`.eq('id', …)`, `.match({ id })`, `.filter('id','eq',…)`) or caps rows with `.limit(1)` — there at-most-one is structural and "not found → null" is the normal intent. `.insert()/.update()` + `.single()` with no id filter **is** flagged: a discarded error there is a silent **failed write**. The raw class is 223 sites; the exemption leaves 193, all pinned by a real pk or `.limit(1)`. Fixes: destructure `error`, or use **`.maybeSingle()`** when 0 rows is a legitimate answer (say it in the source). **The exemption used to accept any `<x>_id`**, and K8 audited that edge against prod's unique indexes: of 209 suppressed sites only 16 rested on it, **half of them pinned by nothing** (`email_sends.postmark_message_id`, `whatsapp_messages.wa_message_id`, `whatsapp_templates.meta_template_id` — de-facto unique, no index) and the other half by **composite** uniques the rule never knew about (`teams(location_id,name)`, `staff_allowances(profile_id,year)`). All 16 are now `.maybeSingle()` and the heuristic is narrowed to `id`. **Blind spot:** one expression only — a chain built across statements/variables, or consumed by `.then(({data}) => …)`, is invisible, and uniqueness lives in the schema an AST rule cannot read, so a composite unique or a unique non-`id` column (`race_events.slug`, mig 451) is an **accepted false positive** — answer it with `.maybeSingle()` plus a comment, never a disable.
- **A BARE `await db.from(t).update(u).eq(…)` is the other half of that class, and the `.single()` rule cannot see it** — nothing is destructured, so there is no discarded binding to flag, and the builder RESOLVES with `{ data, error }` instead of throwing, so a failed write returns a resolved promise and the caller reports success. **The class is repo-wide and its baseline is not clean — but do not quote a site count for it, here or anywhere.** Four revisions of #1472 published four different totals and none survived an independent re-run; grep undercounts it badly (multi-line chains are the house style) and only the AST rule can answer. Measure the path you actually care about instead: add it to the `files` list in `eslint.guardrails.config.mjs` and run `npm run check:guardrails` — the same command the gate runs, so a census and the gate can never disagree. Fix = destructure `error` and handle it as the call site deserves, or run the write through `checkedWrite(scope, () => query, { expectRows, retries })` (`src/lib/checked-write.js`, CHECKEDWRITE.1), which judges the error and the rows and logs a failure; **where the row MUST exist also judge the rows it touched** — `.select('id')` then `data.length` — because a zero-row UPDATE is NOT an error in PostgREST. **A destructure is not automatically a fix:** `const { data } = await <write>` is seen by NEITHER rule (the `.single()` rule only fires on a `.single()` chain), so the write-side rule flags a mutation destructured without `error` too. **And `.then(() => {})` is not a fix either** — a `.then` only counts when its first parameter can reach the error. `check:guardrails` (`no-unchecked-supabase-write`) enforces all of it, **armed PER-PATH** (like `no-low-contrast-accent-text`) because the baseline is not clean: clean an area, add one line to `eslint.guardrails.config.mjs`. **Arm by danger, not by convenience** — the bare writes that read as HANDLED are the dangerous ones: a supabase builder resolves rather than throws, so a wrapping `try/catch` cannot fire for them, which is how `whatsapp-consent.js` shipped a STOP path that answered `applied: true` and texted "You've been unsubscribed" on a write that failed. **Blind spots:** a chain awaited through a variable or handed to a helper that awaits it internally (`campaign-sender.js`'s `writeOrLog`), and zero-row UPDATEs — the rule is a floor, not proof. `mobile/**` is outside `check:guardrails` entirely.
- 🔴 **Removing a silent failure must NEVER create a louder one, and that is the harder half of this class.** BAREWRITE took four review rounds to learn it, each time the same shape: a site was made to "fail closed", and failing closed turned a rare silent-wrong-value into a CERTAIN loss of something the customer needed. **For a customer-facing message, losing the message is worse than the rare wrong value the guard was added to prevent.** Four real instances, every one of them shipped on the branch and reversed before merge: (a) the WhatsApp STOP path returned early on the first failed write, so a partial failure now wrote ZERO suppression signals where main had written one — *attempt every suppression write, collect the failures, then judge*; (b) `resolveEventCommsLocation` threw on an unreadable `locations` row, and `sendRaceConfirmations` is only invoked on a FRESH payment transition (`markRacePaymentStatus` returns `applied: null` once the payment is `completed`), so nothing retried and a paying attendee silently lost their receipt and check-in QR — against a wrong-brand send that **no event in prod can currently produce** (email identity resolves per ORGANISATION, which is structural; the SMS alpha sender is per LOCATION and **UN1T Hatch Street's `UN1THATCH` really does differ from Stillorgan's `UN1T Dub` inside the same org**, so the conclusion rests only on the fact that no Hatch event today is a host event or carries a `sending_location_id` — give one either and the guarantee is gone, so the resolver logs `crossesLocation` for exactly that case); (c) a send-once stamp or claim taken BEFORE the send turns a possible duplicate into a permanent silent loss on a process kill **unless the claim carries a lease something later re-opens** — race-confirmations has no lease column, so it stamps after the send; the WhatsApp drip claim leases on `created_at` and a later tick re-claims a stale one; (d) a lost bookkeeping write on a campaign that `main` silently re-looped was returned as `error`, which reaches `campaignFailurePatch` and can mark the campaign `failed` — a state nothing picks up again. The order of preference is: **log loudly and structurally (`logError`, never free text) → accept a duplicate or a retry → only fail closed when proceeding would do something actively harmful and irreversible.** A lost bookkeeping write is also never grounds to KILL the work: `campaignFailurePatch` flips a campaign to `failed` once `last_error` is already set, and the bundle-disabled gate writes `last_error` every tick, so returning a transient rotation-bump failure as `error` marked the campaign dead on its first blip — it returns `warning` instead, which the cron logs and counts but never feeds to the kill switch.
- **Check `information_schema` before driving a "dormant" column** — mocked tests + `next build` won't catch a column that doesn't exist in prod (assumed `campaigns.postmark_stream`; it's on `email_sends` → prod 500).
- 🔴 **A column named in a `.select()` is a CLAIM ABOUT THE SCHEMA, and no mock ever checks it.** `sequence_enrollments` has no `created_at` (it is `enrolled_at`), yet `enrol.js` selected it from May; PostgREST 400s that on every call, the error was discarded until #1480 made it throw, and **every sequence enrolment in the estate then failed silently for 24 days** — through four months of green tests, because the mocked `.select()` accepts any column string whatsoever. `check:select-columns` now resolves every literal column name against the schema replayed from `supabase/migrations`; a column it cannot prove goes in `.select-columns-allowlist.json` with a reason and a dated expiry, never a disable.
- 🔴 **A name passed to `.rpc()` is a claim about the schema too.** `increment_step_sent`, `increment_sequence_enrolled` and `increment_sequence_completed` never existed (no migration, not in `pg_proc`): PostgREST 404'd every call, supabase-js resolved `{ error }` into a `try { await … } catch {}` that could never fire, and three counters never moved for months through green tests (a mocked `db.rpc` accepts any name). `check:rpc-names` resolves every `.rpc()` name against the functions replayed from `supabase/migrations`; a function made by hand fails it on purpose (prod must be reproducible from the files).
