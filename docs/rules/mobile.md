# Web and mobile boundary

The full rules behind the one-line summaries in `CLAUDE.md`. Moved here word for word from `CLAUDE.md` on 19 Nov 2026 (CLAUDEMD.1); keep the two in step when a rule changes.

**Web/mobile boundary**
- **Mobile CANNOT import `src/lib`** → `shared/` is the seam, consumed as the `shared` file: package (`import { X } from 'shared/permissions'` — never relative `../shared`, which Metro 0.84+/SDK 57 won't resolve out of the project root), and not everything is re-exported. A mobile import of a non-exported name resolves to `undefined` and only crashes at runtime — `npm run check:mobile-imports` guards it (and `mobile/**` triggers Web CI).
- **The emailed login code is `EMAIL_OTP_LENGTH` (8) digits, not supabase's default 6** — Auth → Email → "Email OTP Length" is a dashboard setting on `iyvtbjjxdggiadzwwvdj`, so never hard-code a digit count in a code input, a placeholder or user-facing copy: read `mobile/lib/otp.js`. A short `maxLength` truncates silently and surfaces as "that code didn't work", which reads as a wrong code and points the user at the email. It killed mobile passwordless sign-in from MAGIC-LINK.2 until 2026-08-12, and bit champ-app (same project) a month earlier.
- **Never embed `profiles` from a mobile-direct Supabase select** — the `authenticated` role has no grant on `public.profiles`, so the *whole* select 500s. Route through `/api/*` (service role) for another user's name. `contacts` embeds are fine.
- **Mobile `/api/*` wrappers must build headers via `authHeaders()`/`api()`** — a hand-rolled `Bearer` drops `x-impersonate-target` and breaks "View as user" (reads as a scoping leak).
- **Web parity:** a new `WEB_PERMISSIONS` key must get a mobile counterpart, a `WEB_ONLY_OK` entry (with reason), or `CROSS_PLATFORM_KEYS` — `check:mobile-parity` gates it.
- **A push to `main` touching a bundle path PUBLISHES AN OTA to production phones** (`eas-update.yml`) — **at 100%, to every device on the runtime lane, on next launch**. OTAPCT.1 (2026-08-21) reversed the P5 10% default because a staged rollout nobody ramps BLOCKS the next publish (see the bullet below); at 100 the workflow omits `--rollout-percentage` entirely, so no rollout object and no 48h ramp clock exist. Runtime 2.3.0 is the PUBLIC lane, so that is the member fleet, not staff phones. Staging one is opt-in: `workflow_dispatch` with `rollout_percentage` < 100, which re-arms the block and *does* carry the 48h ramp-or-rollback obligation — `mobile/docs/ota-rollout.md`. The trigger is an **allowlist**, so adding a new directory under `mobile/` means deciding whether it ships: register it in the trigger *or* in `NON_BUNDLE` (`scripts/check-ota-trigger-paths.mjs`). `check:ota-paths` forces the choice (as a **gate** inline in the publish job, and on PRs via the required **Test & lint** check since CI-GATE.1 made `main` branch-protected). Never "fix" an over-triggering path by adding a `!` negation — that is the denylist this replaced. **`mobile/app.config.js` is a publish path**, so `npm run version:patch` — step 1 of both store-submission flows — makes a commit that publishes on the CURRENT runtime lane (`version` and `runtimeVersion` are separate literals); the script no longer pushes by default. Icon/splash art and test-only changes under `mobile/lib/`+`shared/` also publish no-op groups — accepted over-triggers, pinned in `tests/ota-trigger-paths.test.js`.
- **An un-ramped rollout does not "stack" the next publish, it BLOCKS it** — EAS refuses any new update on a `runtimeVersion` that already has a group between 1% and 99% ("Cannot publish a new update with this runtime version while a rollout is in progress"). So a forgotten 10% partial is a **publish outage on that lane**, not a cohort split: `main` runs ahead of every phone, silently. It happened 2026-08-19→20 — one un-ramped group refused the next two publishes and two merged changes reached zero devices, with a red workflow nobody reads as the only signal. `eas-update.yml` **pre-flights** the rollout state before the Metro export and the CDN upload (it prints the stuck group + ramp command into the job summary) and **opens a tracking issue** on any publish failure. 🔴 **The pre-flight runs AFTER `npm ci`, and must**: `eas update:list` resolves the project id via `@expo/config`, which EVALUATES `mobile/app.config.js` — and that file imports `expo/config-plugins`, so with no `mobile/node_modules` it dies with `Cannot find package 'expo'`. It originally ran before the install to save that minute too, which meant it **failed open on every publish from the day it landed and never once ran** (OTAPREFLIGHT.2, three runs verified). Diagnosing it took reading eas-cli: under `--json` the CLI swaps stdout for stderr, but only *after* the project-id/login context resolves, so a context failure writes its one useful line to real **stdout** — which the step captured into the JSON file and deleted unread, leaving only oclif's causeless "update:list command failed." The pre-flight **fails open** — unreadable CLI output, a CLI error, or an unreadable `runtimeVersion` all let the publish proceed — and it never ramps or deletes anything: clearing a rollout is an operator action (`mobile/docs/ota-rollout.md`). Both directions pinned by `tests/ota-rollout-preflight.test.js`, which runs the real workflow shell against a stub CLI.
- **Install mobile deps with a plain `npm ci` — never `--legacy-peer-deps`.** There is no `.npmrc` anywhere in the repo, so EAS Build resolves the BINARY's tree with a plain `npm ci`; a flag on the OTA side can only create the Hermes-ABI tree mismatch the pinned install exists to prevent (the 2026-06-03 boot-crash class). Measured on the current lockfile: the flag prunes **13** entries under npm 11.12.1 (two peer roots — `@react-native/metro-config` with its Metro/Babel subtree, and `@testing-library/dom` with its test-only subtree) and **0** under npm 10.9.4, so the divergence is latent until a Node bump. `eas-update.yml`, `mobile-export.yml` and `mobile/docs/store-release-one-app.md` §7 all agree on this since OTATREE.1; they did not before.
