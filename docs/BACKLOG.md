The campaign sender keeps its existing */2 cron design: it already has claim-before-send + 500-recipient chunk pacing, campaign latency is not operator-visible the way webhook/import latency is, and per-chunk publishes would push the QStash **free tier's 1000-requests/day hard cap** — staying cron-based avoids an Upstash paid plan for zero user-facing benefit. **Invoice OCR (#180 follow-ups)**
- Enable Anthropic prompt caching on the invoice extraction system prompt. The system prompt in `src/lib/invoice-extraction.js` is identical across every call (~500 tokens), so adding a `cache_control: { type: 'ephemeral' }` block to the system message would knock ~50% off the input cost per extraction. Anthropic caches for 5 min by default; at any realistic invoice cadence the cache stays warm. Implementation is ~10 lines in the Anthropic request body + a `anthropic-beta: prompt-caching-2024-07-31` header. Worth doing once monthly volume crosses ~200 invoices/month (cache savings start outweighing the cognitive cost of the beta header).
- Monthly cost true-up review. After the first month of real extractions, pull actuals from `console.anthropic.com` → Usage and compare against the per-invoice estimates (~$0.017 single-page, ~$0.030 multi-page). If consistently higher: likely operators are re-extracting frequently, or operators are uploading huge raw phone photos that should be downsampled before send. Both are easy fixes; the trigger to investigate is "more than 2× the estimate".

**Shelly smart plugs — deferred by decision** (SHELLY-UI.1→.9, 2026-08-23)

The v1 operator surface (`/automations/shelly`, `/api/shelly/*`, migs 562-564) deliberately stops here. Nothing below needs a schema change to add — the tables name no transport and no device class — so each is a decision that was made, not a gap that was missed. `scripts/check-mobile-parity.mjs` points a reader at this heading from its `WEB_ONLY_OK.device_control` note, so keep the heading string as it is.

- **A live on/off toggle on mobile — ✅ SHIPPED (SHELLY-MOB.1, 2026-08-23).** Studio hub → **Smart plugs** (`mobile/app/(staff)/shelly/`): the adopted rows with their freshness chip, wattage and relay state, and an On/Off pill per row riding `GET /api/shelly/devices` + `POST /api/shelly/devices/[id]/toggle` through `api()`. No new server code and no new permission key — it rides the same top-level `device_control` key its routes already enforce, so the parity script needed no change, exactly as predicted here. The AUTHORING half (schedules, adopt/remove, the connection) stays web-only and the screen says so. The prediction that it needed the live-gate answers first held: the toggle's three response shapes (`applied`, `pending`, `holds_until_changed`) are what the mobile copy is written against, and `mobile/lib/shelly.js` re-types the web's freshness thresholds and pending vocabulary because mobile cannot import `src/lib`.
- **Gen1 devices.** v1 is Gen2+ only (the `switch:N` component shape); Gen1's `relays[]`/`meters[]` shape is a second normaliser and a second command path, and discovery already marks those devices unsupported with a reason rather than hiding them. Revisit if a studio actually owns one.
- **The Integrator API transport.** Shelly's consent-based multi-account model (applied for; business email required, timeline unpublished) would remove the "a password change kills the key" trait entirely. It needs a **persistent websocket worker outside Vercel**, which is the reason it is not a drop-in: the swap itself touches only `src/lib/shelly/client.js`, but the hosting is a new thing to run.
- **On-device `Schedule.*` / `Webhook.*`.** Pushing the windows onto the plug itself would survive our cron being down and remove the per-minute reconcile entirely — at the cost of two sources of truth for a schedule, and a divergence nobody can see from either end. Only worth it with the drift mode below.
- **A desired-vs-actual drift mode.** Today the engine acts at boundaries and on overrides; it does not continuously assert that the relay matches what the schedule says, so a plug switched at the wall stays switched until the next boundary. A drift mode would close that, and would also be the honest way to run on-device schedules.
- **Offline / key-rejected alerts.** Both states are already visible (the device card, the connection badge, the Integrations hub card) but nothing pushes them — an owner learns about a dead key by opening the page. The signals exist on the rows; only the delivery is missing.
- **A `?for=<locationId>` hint on the hub card.** The Integrations hub renders a row per in-scope location, but the deep link is always `/automations/shelly`, which opens the ACTIVE location — so a master looking at four rows clicks four links to the same page. A `?for=` hint that pre-selects the location switcher (not a `location_id` the routes would honour — no Shelly route accepts one, and that must not change) is the small fix.
- **Covers and lights** (`set/cover`, `set/light`). The client speaks `set/switch` only. Same schedule vocabulary, different command and a different notion of "state" (position/brightness rather than on/off), so `last_state` would need a shape per class.
- **A `LocationIntegrations` tab.** Shelly configuration lives on the Automations page rather than under Settings → Locations, matching Sonos. Worth revisiting only if a third per-location device integration appears and the pattern starts to read as scattered.
- **An engine rule for unmanaged overrides.** On a device with no schedule (or a schedule switched off), an expired override is never closed — the relay holds as set until a human changes it, and the API says so with `holds_until_changed`. That is the approved v1 behaviour and it is pinned by a planner test. **Revisit only if operators actually expect the "until" they picked to expire** on those devices; the alternative (a cron that switches off a plug nobody asked it to manage) is the worse bug, so this is a decision to re-take deliberately, not a defect to fix.
