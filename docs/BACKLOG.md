**SaaS tenant readiness — bundle enforcement scope decisions (2026-08-16, TENANT.6)**

- **Bundle enforcement is JS-layer only — accepted for UN1T-only operation, MUST be revisited before the first external tenant whose plan excludes bundles.** `isFeatureEnabledAtLocation`/`bundlesDenyKey` (`shared/permissions.js`, BUNDLES.5) is consulted by every web page/route gate and by `hasPermission()` on mobile's `/api/*` wrapper layer — but it is NOT consulted by two other surfaces that can still touch bundle-gated data: (1) **mig 218/219's `private.auth_mobile_can()` SQL RLS function** — it checks a location's fine-grained feature key (`features -> perm_key <> 'false'`) directly against `locations.features`, with zero awareness of `BUNDLE_KEYS`/`bundlesDenyKey`, so a location with e.g. `bundle_sales: false` but no explicit `pipeline: false` override still passes RLS for direct-Supabase mobile reads on `deals`/`notes`/`activities` (pipeline), `bookings` (bookings), and `whatsapp_conversations`/`whatsapp_messages`/`whatsapp_templates` (whatsapp) — every table mig 219 gates through `auth_mobile_can`; (2) **background senders never consult bundles at all** — `src/lib/sequences/*` (scheduler, steps, triggers, enrol) and `src/lib/automations/*` have no `isFeatureEnabledAtLocation`/`hasPermission` call anywhere in their send path, so a sequence or automation configured before a location's `bundle_marketing`/`bundle_messaging` was turned off keeps firing regardless. **Accepted today** because every live location (Stillorgan, Hatch placeholder) is UN1T-operated and every bundle is effectively on (BUNDLES.5's `{}` back-compat default) — nobody is currently relying on a bundle being OFF to keep staff off a table. This stops being safe the moment an external tenant's plan withholds a bundle their staff's mobile client (or a running sequence/automation) can still reach through one of the two surfaces above — revisit then, either by teaching `auth_mobile_can` the bundle map (mirror `bundlesDenyKey` in SQL) or gating the RLS-bypass surfaces some other way, and by adding a bundle check to the sequence/automation runner's per-recipient gate.
- **Multi-location approvers are judged by their ACTIVE location's bundles, not the row's location — accepted, matches the existing per-user-grant precedent.** The approvals registry's bundle check (`bundlesDenyCategory`, Task 2 of BUNDLES.5) reads the CURRENT user's `activeLocation`, the same way every other per-location permission already resolves (`hasPermission`'s `activeAssignment`/`activeLocation` pairing — see `src/lib/permissions.js`'s own header comment). So an approver who holds a cross-location grant and is currently browsing from a bundle-ON location sees pending rows for OTHER locations even where those locations have the relevant bundle OFF — the row's OWN location bundle state is never separately checked. This mirrors a pre-existing, accepted behaviour (a per-user override already ignores the row's location for every fine-grained key), so it's not a new gap introduced by bundles — just an existing precedent bundles inherited. Revisit with a per-row location-bundle check (join the row's location into the registry's bundle test, not just the viewer's) if a tenant complains that an approver can see/act on bundle-off-location rows they shouldn't.

**QStash push migration (QSTASH.1–.10, 2026-07)**
- ~~Migrate `run-campaigns` to QStash push delivery like the other 7 queue-poller crons.~~ — **dropped (Richard, 2026-07-19)**. The campaign sender keeps its existing */2 cron design: it already has claim-before-send + 500-recipient chunk pacing, campaign latency is not operator-visible the way webhook/import latency is, and per-chunk publishes would push the QStash **free tier's 1000-requests/day hard cap** — staying cron-based avoids an Upstash paid plan for zero user-facing benefit. Do NOT "complete the pattern" by migrating it; if campaign volume ever makes the cron a bottleneck, revisit with the QSTASH.8 host-campaigns campaign-kick + chunk-chaining shape (which fits the free tier) rather than per-row publishes.

**Invoice OCR (#180 follow-ups)**
- Enable Anthropic prompt caching on the invoice extraction system prompt. The system prompt in `src/lib/invoice-extraction.js` is identical across every call (~500 tokens), so adding a `cache_control: { type: 'ephemeral' }` block to the system message would knock ~50% off the input cost per extraction. Anthropic caches for 5 min by default; at any realistic invoice cadence the cache stays warm. Implementation is ~10 lines in the Anthropic request body + a `anthropic-beta: prompt-caching-2024-07-31` header. Worth doing once monthly volume crosses ~200 invoices/month (cache savings start outweighing the cognitive cost of the beta header).
- Monthly cost true-up review. After the first month of real extractions, pull actuals from `console.anthropic.com` → Usage and compare against the per-invoice estimates (~$0.017 single-page, ~$0.030 multi-page). If consistently higher: likely operators are re-extracting frequently, or operators are uploading huge raw phone photos that should be downsampled before send. Both are easy fixes; the trigger to investigate is "more than 2× the estimate".

**Revolut authorised supplier payments (design, 2026-05-26 — under review)**
- Full pre-build design at `docs/REVOLUT_PAYMENTS_DESIGN.md`. Closes the AP loop: ingest → Xero bill → **pay** → paid status synced back. No code yet — design only. **Decision captured**: use Revolut Business API's **payment-draft model** (CRM assembles, a human approves the actual money movement in the Revolut Business app), not direct `POST /pay` — the CRM is never the final authoriser. This also keeps PSD2/SCA inside the bank's app. **It's the Business API, not the Merchant API the repo already has** for inbound — separate cert/OAuth auth (JWT client assertion + X.509), separate credentials, periodic human re-consent. 4-phase sandbox-first build planned. Before any build, settle the §10 open questions in the doc (connection scope per-location vs per-org, who approves, can counterparties be created from the CRM or only selected, re-consent cadence). Resume notes section at the top of the doc — update it as decisions land.
