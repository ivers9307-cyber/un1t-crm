Every tool in `src/lib/agent-tools/` declared `studio_id: z.string().uuid().optional()`, so any MCP tool call naming Stillorgan explicitly answered `invalid_input: studio_id: Invalid UUID`. Verified against the live DB: of six locations it is the ONLY one that fails, and `profiles` (20), `contacts` (9212), `shift_templates` (54) and `organizations` (3) all pass — blast radius one row, and that row is the flagship and the only live Glofox studio. The bug is shaped to survive a smoke test: omitting `studio_id` works (`resolveStudio` picks a default and validates nothing), so it only bites the first person who says "at Stillorgan" — and `mcp_tool_calls` is empty, so nothing has ever connected to observe it. The fix already existed and said why: `uuidLike` in `src/lib/schemas.js`, whose comment reads "Zod 4's `.uuid()` is RFC-strict but the seeded location ID isn't RFC-compliant", and which CLAUDE.md mandates over `z.string().uuid()`; MCP.1 did not use it. All 25 occurrences across 18 tool modules swapped, and `tests/agent-tools-guard.test.js` changed from PINNING the strict form to REQUIRING `uuidLike`, so a new tool cannot reintroduce it. Surfaced by the SAAS-10 cross-tenant harness while bridging these tools into the in-app assistant (#2349): its synthetic fixture ids are not RFC-compliant either, so the `create_activity` control failed with `Invalid UUID` and pointed straight at it. |
