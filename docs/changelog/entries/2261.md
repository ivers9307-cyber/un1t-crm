| #2261 | AUDIENCEIDS.1 — audience id lists beyond the GET URL go server-side | 2026-10-31. A `tag` / `event_registration` / `location_list` audience filter resolved to a contact-id list that rode the PostgREST GET URL (`id=in.(…)` / `id=not.in.(…)`) under a COUNT bound of 2,000; the limit is URL bytes (39 per uuid), so the Stillorgan Lock-In Sale campaign with two `tag neq` filters (148 + 1,754 ids, ~74 KB) failed every tick with an EMPTY supabase error and was auto-marked failed. Mig 795 (applied): `contact_location_audience_scoped` and `studio_contacts_scoped` (service role only) return their view's rows at one studio scoped to include/exclude id arrays carried in the rpc body; PostgREST still applies the caller's filters, select, order, range and count, so the `{ query }` contract holds. `audience-filter.js` merges the three virtual fields into ONE include/exclude set (positives intersect, negatives union, exclusion subtracted from a known inclusion), measures the encoded predicate against `AUDIENCE_ID_URL_BUDGET` (8,000 chars, supabase-js's own default), keeps the GET path under it, rebases onto the rpc twin over it (campaign populate/count/preview, WhatsApp audience and reachability, audience-count, eligibility) and throws a loud `InvalidAudienceFilterError` naming the URL length where no rebase exists; the sequence evaluator judges one contact in JS (`pinnedId`). A head:true count on the rpc path is POST + count + limit(1) (postgrest-js puts rpc args on a HEAD URL). campaign-sender records a failed audience load with status, code and URL length (`describeAudienceQueryError`), names a resolver refusal, and sizes the resend non-opener chunk by the URL budget (204), not 1,000. Verified on live data (2,955 − 1,754 = 1,202 both ways) and through PostgREST; the rpc path was not exercised from supabase-js against prod. |
