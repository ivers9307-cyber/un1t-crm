| #2068 | UN1TSYNC — read-only un1t.online sync for Hatch Street | 2026-10-16. Hatch Street books and bills on un1t.online, not Glofox, and the CRM had no data source for it. A GET-only client (`src/lib/un1t-online.js`, studio API token, 60 req/min honoured, any single wait capped at 90s, `pageSize` 100) feeds PII-stripping mappers (`un1t-online-map.js`: integer cents; no `reset_password_*`, next-of-kin, guest details, invoice URLs or embedded users), an organisation-scoped contact resolver (`un1t-online-contacts.js`: `un1t_user_id`, then case-insensitive email inside the org, so a Stillorgan member joining Hatch is attached, never duplicated; fill-only-nulls; new contacts carry `name` because it is NOT NULL) and an engine (`un1t-online-sync.js`) that pulls every list and studio-checks before the first write, upserts eight `un1t_*` tables and never deletes. Memberships reconcile into `contact_memberships` (`source 'un1t_online_api'`); endings fail closed for any member the run could not attribute (a single bad client once froze every cancellation at the studio). Connection write-backs are guarded on a non-secret SHA-256 token fingerprint (rotation keeps `token_id`), never on the token, since a PostgREST filter is a logged URL. Owner/master connect/disconnect/sync-now routes refuse 409 a token for a different studio or a studio already active at another location (`channel_connections_un1t_online_studio_unique`, the Xero mig 554 rule). New membership source `un1t_online` (`'un1t'` stays reserved for built-in memberships), every capability false for now; integration health warns 30 days before expiry and when contacts could not be matched; the `connection-health` cron skips the platform. Cron `un1t-online-sync` every 15 minutes. Hatch classes are deliberately NOT written to `class_occurrences`/`class_bookings` until those readers are audited. Migs 726 (schema) and 727 (heartbeat) were applied to prod before merge.
