| #2369 | TRIALLEAK.1 — a /trial checkout survives a reload, the open order is reused, and a failed or expired one is never a dead end | 2026-11-14. Buyers from Meta ads (mostly the Facebook or Instagram in-app browser) started the €39 trial checkout and did not pay: the checkout lived only in page state, so a reload on the way back from a banking app lost it, the order failed 30 minutes later, a pending return to `?purchase=` spun for ever and every retry made another row and Revolut order. Now the payment step puts `?purchase=<id>` in the URL and a load with it remounts the embedded checkout on the same token (the status route answers `resumable`); a pending Stillorgan return ends after the poll budget with a message; the checkout's poll hands a failed or timed-out order back to the form with the details kept (also kept in the tab's sessionStorage, so a cancelled Hatch checkout lands on a filled form saying nothing was charged). A caller that names the purchase id its own browser holds (`resume_purchase_id`) gets its own open Revolut row back instead of a new one; an email or phone alone never does (security review). Trial orders live two hours (`src/lib/trial-checkout-window.js`: expiry, the 110-minute reuse window and `resumable` from one constant); a checkout that cannot be opened marks its row `failed` (`checkout_not_opened`); `last_error` records `checkout_expired` / `checkout_cancelled` / `payment_declined`. Inside Facebook or Instagram the payment step offers a link to copy that resumes in the buyer's own browser. `trial_purchases.attribution` gains `utm_source`, `utm_medium` and `in_app_browser`; /start and /50plus carry source and medium in `funnel_events.meta`; an unfilled Meta URL macro (`{{ad.id}}`) is treated as absent everywhere ad values are captured (capped to 200 first, linear test). No migration. |
