The MCP spec's §4 follow-up: the assistant had its own copy of nine tools `src/lib/agent-tools/` already implements, drifting independently. **Seven now run the registry bodies through a second door.** `runToolAtStudio` is extracted from `runTool` (parse → build ctx → apply the tool's gate → run → map a `ToolRefusal`); `runTool` keeps everything MCP-specific — the rate limit, `resolveStudio` (a studio the person holds `mcp_access` at), the `org_settings.mcp_enabled` switch, and the `mcp_tool_calls` row. **That last one is load-bearing**: assistant traffic in that table would destroy the only signal for whether anything has ever connected over MCP. MCP behaviour is unchanged (its 121 tests untouched and green). The new door, `src/lib/assistant/tool-bridge.js`, forces the studio to `user.activeLocation` and strips `studio_id` from BOTH the advertised schema and the input, so neither the model nor anything steering it (text in a contact note it has just read) can redirect a tool to another studio. Schemas are derived once via `z.toJSONSchema()` minus `studio_id` — **not** zod's `.omit()`, which throws on objects carrying refinements ("cannot be used on object schemas containing refinements") as `get_shifts` and both reports do; parsing keeps the full schema so refinements still run. **GATES (Richard's decision, 11 Nov 2026): the registry's, replacing the flat role tiers — and the one material change is a WIDENING, the opposite of what was expected.** `contacts` defaults to `true` for every role including staff, and the registry gates `search_contacts` on that key with NO role floor where the assistant demanded the manager tier, so a staff member can now search contacts in the assistant (consistent with the Contacts screen they can already open, and with MCP); pinned by an explicit test, and reverting is one clause in `search-contacts.js`'s gate.
