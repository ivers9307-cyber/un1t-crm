| #2430 | INBOXASSIGN.1 — inbox threads can be owned: assign to me, to a colleague, or unassign, on WhatsApp, Instagram and Mail | 2026-11-17. `assigned_to` existed on `whatsapp_conversations`, `instagram_conversations` and `email_tickets` and nothing wrote it (the ticket-era EMAIL-ASSIGN.1 routes went with RETIRE-TICKETS.2), so two people could answer the same customer. New `GET`/`POST …/assign` next to each channel's thread routes (`/api/whatsapp/conversations/[id]/assign`, `/api/instagram/conversations/[id]/assign`, `/api/email/mail/[id]/assign`), each behind that channel's own thread gate (WhatsApp at the thread's studio; the Instagram routes' gate; `loadConversationForUser` for Mail). One shared module, `src/lib/inbox-assignment.js`: a named owner must be an active, non-deleted member of the thread's studio who holds the channel there (web or phone `whatsapp`; Mail: `email_inbox` plus sight of the mailbox), resolved through the same tiers as `hasPermissionForLocation`; the picker returns `{ id, full_name }` only; the write is pinned to id and studio, its error checked, and a zero-row write is a 409. Writes nothing but `assigned_to` (no timeline row). UI: an "Assigned to" select in each thread header (`AssignControl`), an Anyone / Mine / Unassigned filter on the inbox list and on Mail (server-side `owner=` there), and the owner on each row (`OwnerTag`). The existing pushes already page only an owned thread's owner. Instagram is the same code path but cannot be tried live (no account connected). No migration, no mobile change. Tests: `inbox-assignment.test.js`, the three route tests, `owner-filter.test.js`, `AssignControl.test.jsx`, `UnifiedInbox.owner-filter.test.jsx`. |
