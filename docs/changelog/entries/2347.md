| #2347 | ASSISTREG.1 — the assistant's contact search term is sanitised, and the registry migration is scoped | 2026-11-11. Found while scoping the MCP spec's §4 follow-up (move the in-app assistant's `TOOLS`/`TOOL_PERMISSIONS` onto `src/lib/agent-tools/`). `search_contacts` in `src/app/api/assistant/chat/route.js` interpolated the model's query raw into the PostgREST `.or()` string, which is two defects in one line and both are reachable by any text the model can be induced to emit — a contact note it has just read included: a `,` closes the clause and opens another, so the caller filters on `contacts` columns the tool never offered (a filter oracle over the studio's contacts), and `%`/`_` are LIKE wildcards, so a bare `%` matches everyone. Provable rather than theoretical: the suite's in-memory PostgREST mock really does split `.or()` on commas and really does treat `%` as a wildcard, so `alice,phone.ilike.%87999%` returns a contact whose name and email match nothing, purely through the smuggled phone clause. **Never a tenant leak** — the `.eq('location_id', locationId)` is AND'ed with the `.or()` group, so the reach was always the one active studio. Fixed where the defect is: the same `sanitizeSearchTerm` the registry's `search-contacts.js` uses, plus the `" \` strip PostgREST needs inside an `.or()` value, and a refusal naming the stripped characters below `MIN_CONTACT_SEARCH_LEN` (2); reach unchanged (same studio, same name + email columns, same manager tier). The registry's own body was deliberately NOT adopted for this tool: it also reads org-sibling contacts through `contact_studios` (ORGCONTACTS.2) and the registry gates that wider reach on the **Contacts** permission, while the assistant gates on the manager tier alone — sharing the body without the gate would put wider data behind a weaker gate. That entanglement is the migration's real shape, measured here for the follow-ups: of the nine tools the two systems share, **only `create_activity` returns the same shape** (the other eight differ, so a single-shot migration would rewrite ~40 of the suite's 54 `executeTool` assertions in the same PR that does the migration — destroying the net the spec nominated); **six have gates equivalent to the assistant's tier** (`create_shift`, `list_staff`, `list_shift_templates`, `get_shifts`, `get_time_off`, `get_holiday_allowance`) and are migratable under parity; and **three cannot move without a gate decision** (`search_contacts`, `create_contact`, `create_activity` — each registry gate adds a permission key the assistant does not check). `get_shifts_for_week` is also not a rename of `get_shifts`: it promises the Monday-to-Sunday week the date falls in (SCHEDHYGIENE.1), which the registry tool has no mode for. Checked and NOT a defect: `user.role` is active-location-aware (`resolveActiveLocationRole`) and the assistant acts on that same studio, so its tier gate judges the right studio. Three tests added, two of which fail on main; the other 54 assertions untouched and green. |
